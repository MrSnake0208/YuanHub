# 私有成就与羁绊资料

## 存储与权限

真实成就、奖励物品、分类积分档位、羁绊组合只由资料所有者手动导入数据库。代码、前端构建包和后端 JAR 不携带这些资料。启动、部署及目录 GET 不写入或恢复资料；缺失目录返回虚拟空目录，数据库故障仍报错。已有个人记录不会因为配置缺失而删除。

部署环境设置 `SHARE_ARCHIVE_DATA_OWNER_ID` 为资料所有者的站内用户 ID（不是游戏账号 ID、邮箱或昵称）。也可在服务器私有配置中设置 `share.archive-data-owner-id`。该账号须激活且具有 SUPER_ADMIN 或 PLATFORM_ADMIN；其余管理员没有成就/羁绊目录管理和投稿审核权限。未设置则全部拒绝管理。该限制包含管理读取、导出、草稿修改、导入、发布、回滚和投稿采纳；普通用户填写自己的记录不受影响。

不要把所有者 ID、数据库凭据或真实资料放入仓库、CI 参数、构建环境变量、日志或 Release 附件。数据库管理凭据仍可直接访问数据，网站展示的已发布条目也仍可被获准访问的用户看到。此功能不承诺数据绝对不可见。

## 数据模型

`achievement_catalogs` 的 draft、published.content 和 history[].content 增加：

- `reward_items`：`{item_key, name, games}` 数组，是该快照的奖励字典；最多512项，键唯一，名称和适用游戏必填。
- `point_tracks`：`{category_id, item_key, tiers:[{at, name, quantity, icon}]}` 数组。按分类稳定 ID 关联，积分物品引用当前游戏字典；每类1–20个递增档位，目标和数量为正安全整数，图标为 coins/ticket/title/frame。
- `reward_filter_keys`：最多20个不重复奖励键，决定玩家筛选选项。

这些字段缺失时视为空配置；不回退到代码内置资料。三项与成就目录在同一文档内以 revision CAS 保存、发布和恢复。设置与条目不匹配时拒绝写入，预览明确显示设置变化。现有目录没有字典时仍可读取，带结构化奖励的维护须先导入对应字典。旧历史若缺字典，不能直接恢复为新发布版；先导出核对并手动补齐草稿，不静默补数据。

玩家目录只返回已发布条目、积分配置和筛选名称，不包含完整奖励字典。投稿奖励选项仅包含当前游戏已发布有效成就实际引用的奖励。羁绊响应 `achievement_targets` 从当前游戏已发布成就的 `linked_metric=yuan_bond_variants` 正整数目标推导，不硬编码档数或门槛；没有目标时前端显示未配置。

## 手动导入

日常成就目录格式仍为 `yuanhub-achievement-catalog` / schema_version=1；catalog 内可携带上述三项。`keep` 只填空设置，`update` 明确替换文件提供的设置；省略字段保留当前设置。首次无正式 ID 的分类临时引用也用于 point_tracks，后端一次性映射到新 ID。保持原有预览、确认草稿、预览发布、确认发布步骤。

成就管理页“奖励字典与积分配置”支持独立配置文件：

```json
{
  "format": "yuanhub-achievement-settings",
  "schema_version": 1,
  "game": "如鸢",
  "reward_items": [{"item_key":"test_coin","name":"测试币","games":["如鸢"]}],
  "point_tracks": [],
  "reward_filter_keys": ["test_coin"]
}
```

此示例仅解释格式，不得作为生产资料。独立配置上传不会立即写数据库：核对摘要→应用到本地草稿→保存草稿→预览→发布。`point_tracks` 可使用目标分类 ID；外部初次整理文件也可使用唯一的 `category_name`，页面显示当前游戏上下文并映射到已有分类 ID，重名/缺失/名称与 ID 不一致均拒绝。服务端只接受 category_id。

羁绊继续使用 `/bonds/admin` 手动预览文件、合入本地草稿、保存、发布。只上传正式条目；来源、内部溯源字段及 pending 留在本地。成员必须通过现有密探和游戏可用性校验，不自动扩展密探目录。

## 切换、恢复与验证

1. 所有者先备份生产对应完整目录文档及个人档案；备份存在仓库外私有位置。后台 published/draft 导出仅是维护文件，不是完整数据库恢复镜像。
2. 发布新代码并在服务器私有配置中设置所有者账号。已有目录保持可读；空库不自动填充，管理操作必须显式触发。
3. 已有生产目录：先用生产后台导出的正式 ID 文件维护，再手动导入奖励配置并发布。不能把另一环境带正式 ID 的目录作为初次导入；成就导入器会拒绝未知身份。
4. 空生产目录：首次导入省略 achievement_id，分类使用临时引用；文件可同时携带字典和积分配置。发布后导出目标环境的正式 ID 底稿。羁绊保留经校验的本站 ID，不能复用另一游戏的 ID。
5. 核对数量、奖励/档位、羁绊目标和原玩家记录。重复发布、重启不会重新灌入；配置错误保留旧发布版并修订草稿。目录历史恢复也必须通过同样校验。

不要通过自动启动脚本、迁移钩子或部署脚本代替手动导入。不要对共享开发/生产库跑测试。定向数据库检查使用 TestMongo 自有 disposable 副本集；单元和容量测试使用合成数据。

历史清理单独进行：当前文件删除不代表 Git 历史、旧构建包、PR 或 fork 已清理。历史重写前冻结引用并保留私有恢复备份；核对 tag/SHA 与部署状态，获得明确强制更新批准后再执行。既有部署按精确 SHA 构建，历史改写后须重新核对发布引用，不能机械重新触发旧标签。
