# 邮箱待领取奖励：独立轻量模型（仅规划）

状态：未实施；本轮仅调查和设计，不改变库存交换协议、MaaYuan扫描或领取行为。

## 现状与边界

当前网页实际导入 `myshare-inventory-exchange` v2；业务记录只有 `reward_delta` 和 `stock_snapshot`。奖励导入会进入获取统计，并根据发生时间和库存盘点基线决定是否增加当前库存。把待领取奖励当作奖励增量会错误增加库存；即便通过早时间强制成为history_only，也会错误增加已获取统计，不能这样复用。

体力日程的 `mail` 获取来源是单日预测值，目标天数模式 `goalReserveSources` 是界面内的规划储备，精确求解可分配 `reserveSources` 至日期；它们不是邮箱清单，不拥有领取事实、到期、云端跨设备状态或库存事务。可复用数量/日期和求解输入，不能把其中任一项当成已领取证明。

需区分四个事实：每日模板是预计获得；游戏已发到邮箱但未领取是待领取；用户确认领取是实际发生；当前库存是否已包含由库存流水/盘点决定。扫描只能读取余额，不能根据余额变化推断具体邮件已领取。

## 推荐数据模型

独立Hub集合 `mail_reward`，复用既有子账号鉴权、revision CAS和账户删除清理，不扩展库存v2枚举。

```text
userId, accountId, id(UUID), revision, updatedAt
title, originChannel, originGameDay?           # 已知来源业务日；不是实领时间
receivedAt?, expiresAt?
items: [{id, count}]                          # 仅已有库存目录的真实道具
staminaAmount: integer >= 0                   # 与白金币/道具余额完全分开
claimState: pending | claimed
inventoryDisposition: unaccounted | recorded | covered_by_snapshot
claimedAt?, inventoryRecordId?, coveredBaselineAt?
plannerReserveId?, plannedClaimDate?          # 可选规划关联，不构成领取事实
```

白金币保留 `items.id=baijinbi`；体力只保存于 `staminaAmount`，不新增假库存道具。账号游戏从已有SubAccount取得。新邮件默认pending/unaccounted；手工邮件ID是主要身份，相同名字、数量、日期都不足以自动认定重复。已知月卡来源可额外保存 `monthly-card + originGameDay` 业务身份，并在该账号下限制唯一；未知来源不猜测。

第一版每封邮件整单领取，不做部分领取、自动识别、自动领取或MaaYuan新协议。若同一封邮件涉及不同实领时间，由用户在领取前拆分为独立条目。

## 状态变化与去重

| 用户操作 | 状态与库存效果 |
| --- | --- |
| 手工添加或编辑待领取 | pending/unaccounted；不导入奖励、不影响当前库存或获取统计 |
| 仅加入规划 | 保持pending；通过mail ID关联一次性储备，在选定预计领取日期可用；不生成每日固定模板、不改变库存 |
| 确认已领取且未盘点 | claimed/recorded；实际领取时间生成稳定record_id，调用现有reward_delta；体力只更新邮箱领取事实/规划储备关联 |
| 确认已领取且已经盘点 | claimed/covered_by_snapshot；保存盘点关联，不增加库存；用户另选补标统计时，以真实领取时间写原有history_only流水 |
| 后续扫描 | 沿用库存快照覆盖流水的原有语义，不自动改变pending邮件、不从扫描推测领取 |

库存关联与领取状态变化需在同一个Hub Mongo事务中完成，revision参与CAS，重试使用相同mail ID与record_id；响应丢失时先读取当前领取状态及流水再重试。同一封邮件不能产生第二笔收入。邮箱操作与快捷录入共享已知月卡业务身份时应复用同一每日ID；若来源游戏日与实际领取日不同，保留originGameDay并使用claimedAt作流水发生时间，不将发信时间当实领时间。

当前快捷入口按所填实际发生时间构造每日ID，无法自动识别多天积压邮件。导入报告也可能使用另一平台ID。因此第一版必须提供“关联已有流水/已包含盘点”选项，并在不确定是否已扫描/快捷录入时停留在待核对状态；禁止仅凭数量相等自动合并或自动加库存。月卡积压的originGameDay如无法确认，要求用户核对，不能伪造新日常来源ID绕过去重。

标记盘点覆盖必须由用户确认已经实领，且对应道具存在完整或listed盘点基线，实领时间不晚于该基线。最新扫描若发生在实领之前，不能声称已覆盖。补标复用现有 `validateDailyAnnotation` 思路及后端覆盖规则，不能借“已包含库存”再加一次余额。

已经入账的邮件不允许直接退回pending或修改原奖励数量；纠错走原有流水删除/恢复，再明确修正关联。第一版仅允许删除pending邮件，已领取保留审计关联。领取成功后撤销其未使用规划储备；如果此前已应用到固定日程，提示用户显式重算，保留历史预测与手工支出，禁止同时作为已领取储备和待领取储备再算一次。

## 预计代码范围

1. 后端新增一个MailReward实体、Repository、Service、Controller；复用账号鉴权/CAS/Hub事务，调用现有InventoryService导入/查询，补账户删除级联和事件通知。
2. 前端库存记录奖励工作台增加“邮箱待领取”轻量列表/编辑区域，API与纯状态转换模块；独立展示待领取合计，不叠加当前库存。先手动管理，复用现有弹层焦点、错误与保存状态。
3. 体力规划增加按mail ID关联一次性储备的明确动作，沿用精确求解储备分配；普通日程用一次性mail来源，不增加每日模板。跨清单引用同一储备需明确互斥，不能每份清单重复消耗同封邮件。
4. 测试涵盖账号隔离、CAS、重试、实际领取/盘点先后、库存事务回滚、扫描与报告的不同ID冲突、体力单次引用和删除级联；真实事务仅在自有可抛弃Mongo容器运行。

预计为独立L3任务，约3–5个工作日含定向测试与人工验收；涉及库存事务与邮箱/规划关联，需另行授权实施，不在本轮扩张。

## 验收与主要风险

| 场景 | 预期 |
| --- | --- |
| 邮箱白金币65＋体力60尚未领 | 当前白金币、获取统计不变；体力只能作为指定日的待领取规划储备 |
| 领取按钮双击、请求成功后断网重试、另一设备同时领取确认 | 一笔领取事实、一条稳定流水；CAS冲突可恢复，余额仅增加一次 |
| 先实领后Maa扫描，再确认盘点覆盖 | 不增加库存；可选补标只补历史，不假造实领时间 |
| Maa扫描后才实际领取 | 作为新收入；不以旧基线冒充已包含 |
| 同日月卡已通过快捷或外部报告录入 | 提供关联/冲突说明；不以新UUID自动再入账 |
| 邮件过期、跨账号、跨清单、已使用储备 | 过期不进入后续预计领取；账号互相隔离；同一储备不重复消费；清单历史不静默改变 |

最大风险是“扫描余额没有邮件身份”，第一版只能由用户确认关联事实，不能承诺自动消除不同record_id的重复。其次是实领时间/原来源日、领取事实与库存事务、储备跨清单引用，以及已领取记录纠错后可能存在更晚盘点。上述边界应以明确选择与原有流水规则处理，不引入全站通用状态引擎。
