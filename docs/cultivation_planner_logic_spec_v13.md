# 培养体力规划器：逻辑、数据基础与交互规范（v13）

## 1. 文档目的

本规划器用于把“培养清单中的材料缺口”转换为连续的每日体力获取 / 支出计划，并在用户修改任意一天后，自动向后传播材料状态、更新未来推荐，同时保留用户已经手工固定的未来日期。

规划器是模拟器，不追踪或回放真实流水。每次进入或刷新时，以当天的当前库存快照作为唯一初始状态，以缩短完成天数为目标生成推荐；当前实现为滚动贪心，不保证全局最短。编辑日程时提供“零额外投入”和“每日购买两次体力（100 白金币 / 日）”两种方案选择。

### 1.1 当前实现与最新交互约定（2026-09-12）

以下是当前实现边界；后文优化器设想不表示已实现精确最短天数求解。

- 从当前密探数据计算经验、修为与化极道具需求；等级突破道具不参与体力模拟、推荐、进度或完成判定。五铢钱、心纸也不参与体力优化。密探详情仍展示完整养成需求。
- 账号库存只抵扣一次。密探卡片与模拟器对参与规划的材料使用相同的共享分配口径。
- 推荐在每次刷取后更新剩余缺口，在所有已开放类别及 6-24 中比较有效收益/体力。不会为了耗尽体力继续刷无缺口素材；伴随掉落可以富余。
- 历练与 6-24 的手动添加、改层数、恢复旧日程统一按规则表结算。派遣只消耗体力，无素材产出；旧日程中的派遣奖励配置也不生效，不提供派遣奖励编辑器。
- 当日产出按完整掉落累计，补缺仅计填补目标的部分；产出 = 补缺 + 富余。全部目标材料和伴随产出可查看，不再只显示前六项，也不会把尚有缺口的材料四舍五入为 100%。
- 编辑态与展示态共用材料进度列表。新增、移除、输入次数与变更层数即时重算当天及后续未固定日期。培养推进面板只保留 resource-list；错误提示位于日程区域。
- 超支、同类别历练合计超过 6 次、未开放层数、购买超过 8 次、非整数次数会使该日无效，暂停该日与后续进度，不虚增材料。
- 备齐即结束周期；无可推进渠道则停止并列明原因，不补出几十天无效日程。90 天仅为搜索上限，达到上限不等同于证明不可完成。
- 方案对比只在编辑态显示，以紧凑按钮选择购买偏好；共用库存起点与派遣偏好，不套用手工日程。固定日不被偏好选择覆盖，无可估算完成日期时累计费用显示待定。
- 编辑态培养清单无排名序号；列表保留至少五张卡片的高度。排序仍在优先模式下影响分配。
- 固定日程与偏好按账号和培养清单隔离；旧版账号级日程保留在默认特别关注清单。周期外固定日保留，可打开检查或恢复推荐。
- 每次重新访问追踪标签或刷新时同步库存和密探资料。不写真实流水或扣减真实库存。
- 当前采用完整一天的 288 自然恢复 + 120 进膳预算；不模拟满体损失，日末结余不自动结转，额外储备可手工填写。每次购买恢复 60 体力仍是可替换规则假设。

它同时支持两类规划目标：

- **整体完成**：目标是尽量缩短整张培养清单全部完成的时间。此模式下，清单排序只影响展示，不应该改变优化结果。
- **优先完成密探**：按用户指定的密探顺序，优先让前面的密探尽早完成。此模式下，清单排序会真实改变每日副本分配和单个密探完成顺序。

正常编辑模式下，购买体力次数由用户在“推荐偏好”中主动指定；系统可以提供方案对比和性价比信息，但不能静默替用户改变购买次数。只有进入独立的“目标天数规划”功能后，系统才反推满足期限所需的最低购买次数 / 额外体力。

## 2. 已确认的游戏数据基础

### 2.1 每日固定体力

- 自然恢复：**288 / 日**（5 分钟恢复 1 点）
- 每日进膳：**120 / 日**
- 不含购买、活动、邮箱、礼包、储备的基础日体力：**408 / 日**

公式：

`E_base = 288 + 120 = 408`

### 2.2 白金币购买体力的价格阶梯

当前已知的是“购买次数 → 当日累计白金币成本”，但**尚未确认每次购买恢复多少体力**。

| 当日购买次数 | 累计白金币 | 第 n 次边际价格 |
|---:|---:|---:|
| 0 | 0 | - |
| 1 | 50 | 50 |
| 2 | 100 | 50 |
| 3 | 200 | 100 |
| 4 | 300 | 100 |
| 5 | 450 | 150 |
| 6 | 600 | 150 |
| 7 | 850 | 250 |
| 8 | 1100 | 250 |

因此规划器可以明确展示购买档位的**白金币边际成本**，但在正式计算“白金币 / 体力”之前仍需要补齐“每次购买恢复体力”这一条规则。

### 2.3 派遣体力支出

| 派遣 | 单次体力 | 时长 |
|---|---:|---:|
| 洛阳 | 72 | 8h |
| 寿春 | 80 | 8h |

日体力账本中，派遣属于**体力支出**，与历练、6-24 同级，而不是“今日体力来源”的一部分。

洛阳、寿春均无培养素材产出，只作为重要的体力支出项参与预算。

### 2.4 6-24

- 单次消耗：**10 体力**
- 单次固定奖励：
  - 五铢钱 34,500
  - 兵书残卷 38
  - 紫星曜 3

规则定位：

- 五铢钱与紫星曜**不属于培养缺口优化目标**，只作为顺带收益展示。
- 兵书残卷会反馈到经验缺口，因此 6-24 可以作为剩余体力的 fallback / optimizer action。
- 即使 6-24 的钱 / 紫星曜收益很多，也不能因此把它们当成“需要补齐的 shortage”。

### 2.5 历练每日奖励次数上限

风火 / 地水 / 阴阳 / 经验四个类别，**每一类每天最多获得 6 次奖励**。当前设计按“类别总上限”处理，不是“每层 6 次”。

## 3. 规划目标与 shortage 定义

### 3.1 纳入优化的缺口

培养清单中可通过体力活动获得的培养材料，应该合并成 shortage vector。例如：

`D = {水镜, 星汉镜, 宝石镜, 经验, ...}`

每个密探保存自己的 shortage，整体最快模式再做聚合。

### 3.2 明确排除的 shortage

以下项目不参与“必须补齐”的优化目标：

- 心纸碎片
- 五铢钱
- 紫星曜

其中五铢钱与紫星曜可以作为 6-24 的**顺带收益**展示，但不能驱动刷取计划。

### 3.3 经验 shortage 的 canonical 表示

推荐后端保存“原始经验缺口（XP deficit）”，而不是把 `残卷 m + 全卷 n` 当成两个独立必须补齐的 shortage。

正确方向：

1. 保存角色需要的 XP deficit。
2. 保存残卷 / 全卷对应 XP 的换算值。
3. 各经验关卡、6-24 的书本产出换算成 XP yield。
4. 优化器对 XP deficit 做状态更新。

目前仍缺“残卷 / 全卷 → XP”的精确换算，因此 demo 只能用简化经验等价值演示状态传播。

## 4. 数据模型

### 4.1 CultivationList

建议字段：

```json
{
  "id": "list_001",
  "strategy": "overall_fastest | priority_agents",
  "agent_order": ["agent_fazheng", "agent_zhenji", "agent_guojia"],
  "preferences": {
    "luoyang_dispatch_per_day": 1,
    "shouchun_dispatch_per_day": 1,
    "stamina_purchase_count_per_day": 2
  }
}
```

### 4.2 AgentTarget

```json
{
  "agent_id": "agent_fazheng",
  "display_order": 1,
  "targets": {
    "level": 100,
    "cultivation": 17,
    "fate": "2-star"
  },
  "shortages": {
    "水镜": 450,
    "星汉镜": 360,
    "宝石镜": 100,
    "xp": 1800
  }
}
```

### 4.3 DailyPlan

同一天应同时保留三层状态：

- `recommended`：优化器当前生成的推荐。
- `planned`：用户真正保存的计划。
- `actual`：未来如果做执行追踪，可记录真实完成值。

```json
{
  "date": "2026-09-12",
  "recommended": {"gains": [], "spends": []},
  "planned": {"gains": [], "spends": []},
  "manual_override": true,
  "actual": null
}
```

`manual_override = true` 是关键：未来重算时保留该日期用户计划，不静默覆盖。

## 5. 每日体力账本

### 5.1 基础公式

在规则补齐后，正式公式应为：

`E_available(d) = 408 + E_purchase(d) + E_extra(d) + E_reserve_used(d)`

`E_spent(d) = 72 * L(d) + 80 * S(d) + Σ[action_count * action_stamina_cost]`

`E_balance(d) = E_available(d) - E_spent(d)`

其中：

- `L(d)`：洛阳派遣次数
- `S(d)`：寿春派遣次数
- `E_purchase(d)`：当天购买体力总量
- `E_extra(d)`：活动、邮箱、礼包等额外来源

### 5.2 获取与支出必须对称建模

**体力获取**：

- 自然恢复
- 每日进膳
- 购买体力
- 邮箱储备
- 活动奖励
- 礼包 / 补偿
- 自定义来源

**体力支出**：

- 洛阳派遣
- 寿春派遣
- 风火历练
- 地水历练
- 阴阳历练
- 经验历练
- 6-24
- 自定义支出

每个渠道都有稳定代表色与 label；展示态和编辑态必须复用同一套视觉语义。

## 6. 推荐偏好与购买体力

### 6.1 正常培养策略

购买体力次数属于**用户偏好**，与派遣次数同级：

- 洛阳派遣：`0..n / 日`
- 寿春派遣：`0..n / 日`
- 购买体力：`0..8 次 / 日`

规划器必须按用户选择的购买次数生成当前推荐，而不是自动把用户切换到更高购买档。

### 6.2 性价比信息

默认方案对比提供：

- 0 次 / 日：最省白金币
- 2 次 / 日：100 白金币 / 日

用户仍可在编辑态修改每日购买次数；修改后的当前设置可以作为额外对照，但不替换上述默认两种方案。

性价比比较应基于：

1. 边际白金币成本；
2. 增加的日体力；
3. 是否真实缩短 ETA；
4. 是否已经被历练类别 6 次 / 日等硬上限卡住。

如果多买体力并不能缩短完成天数，方案对比必须明确显示“额外投入但 ETA 不变”，而不是盲目推荐。

## 7. 两种常规优化模式

### 7.1 整体完成

目标：最小化整张培养清单的最终完成日期。

关键性质：

- 把所有密探 shortage 聚合后求解。
- 清单排序**不参与优化目标**。
- 用户可以调整排序以改变展示顺序，但排序本身不能改变 ETA 或推荐副本组合。

### 7.2 优先完成密探

目标：按用户指定顺序尽量提前完成密探。

推荐使用 lexicographic objective：

`min (T_agent1, T_agent2, T_agent3, ...)`

或实现为强权重：

`Score = W1 * progress(agent1) + W2 * progress(agent2) + ...`

且 `W1 >> W2 >> W3 ...`。

因此此模式下拖拽顺序会真实影响规划。例如整体效率最高的阴阳·十二可能被部分替换成阴阳·十，只因为这样可以让第一优先级密探更早补齐宝石镜并提前完成。

## 8. 日计划求解与副本选择

每天求解输入：

- 当天开始时每位密探的剩余 shortage；
- 用户的派遣次数与购买体力次数；
- 当天额外体力来源；
- 类别奖励次数上限；
- 副本体力成本；
- 各层固定产出。

每天求解输出：

- 获取渠道与体力总量；
- 派遣支出；
- 每类历练各层次数；
- 6-24 次数；
- 当天结束后的 shortage state；
- 单密探与整体完成进度。

推荐采用“整数规划 / 动态规划 / 小规模枚举 + greedy”混合方案。由于每天历练上限很小，单日可行组合数量有限，可以准确求解后再做跨日滚动。

## 9. 用户修改某一天后的向后传播

这是规划器最关键的状态逻辑。

### 9.1 正确状态链

`体力获取 → 可用体力 → 体力支出 → 素材产出 → 剩余 shortage → 下一日`

因此：

- **只增加获取体力**，但不增加支出：材料 shortage 不变，只会增加当天剩余 / 储备。
- 增加历练或 6-24 支出：会改变当天产出，从而改变后续材料缺口。
- 减少某个历练：相应 shortage 会延后到未来日期。

### 9.2 自动重算范围

当用户修改日期 `d`：

1. 保留 `d` 的 `planned` 作为手工约束。
2. 用该日 planned action 结算新的日末 shortage。
3. 从 `d+1` 开始重新计算 future `recommended`。
4. 未来没有手动修改的日期，直接采用新的 recommended。
5. 未来已有 `manual_override=true` 的日期，保留用户 planned，不静默覆盖；以该 planned 继续结算并向后传播。

这意味着“后续材料缺口必须自动更新”，但“后续用户计划不会被偷偷改掉”。

### 9.3 过期计划提示

如果前面变化导致未来某个手动日期计划已经不合理，例如刷一个已经补满的材料，应提示：

`该日计划可能已不再需要 · 查看调整建议`

但默认不强制替换。

## 10. 日期、阶段与展示态

### 10.1 展示态

展示态用于每天快速查看，建议包含：

- 预计全部完成天数
- 总体进度
- 今日结余
- 今日购买体力次数 / 白金币
- **培养清单的紧凑展示**（密探 chip）
- 日期切换
- 今日方案（获取 / 支出 channel chips）
- 培养推进（从当前库存起点的模拟状态、今日模拟新增）

展示态必须明确标注模拟语义：左侧「今日方案」与右侧「培养推进」都从当天最新库存快照开始模拟，按最短完成天数生成推荐。右侧的「今日模拟新增」是本次模拟执行推荐支出后的结果，不是实际刷图流水；规划器不依赖 `/v1/inventory/acquired`，实际流水不会改变当前模拟，下一次同步库存后自然反映。

展示态不出现：

- 方案对比
- 目标天数限制设置
- 推荐值对照输入框

### 10.2 编辑态

编辑态包含：

- 左侧培养策略
- 可拖拽培养清单
- 推荐偏好：洛阳、寿春、购买体力次数
- 右侧自己的日期切换器（不能横跨左侧培养策略）
- 当日获取 / 支出编辑器
- 添加获取 / 添加支出菜单
- 方案对比
- 保存 / 恢复推荐

### 10.3 阶段生成

“阶段”不是硬编码，而是对连续相似日推荐的压缩总结。

阶段边界可以由以下事件触发：

- 某个关键 shortage 归零；
- 最优副本层级组合变化；
- 某类别不再需要打满 6 次；
- 第一优先级密探完成；
- 进入经验收尾 / 6-24 承接阶段。

单日额外体力属于“特殊日计划”，不一定要拆成一个新阶段。

## 11. 方案对比

方案对比**只存在于编辑态**。

默认提供两种固定对照：

- 0 次购买 / 日
- 2 次购买 / 日（100 白金币 / 日）

如果用户在编辑态改动购买次数，可额外保留当前设置作为第三张对照卡，但不替换默认的两种方案。

每个方案展示：

- 预计完成天数
- 每日购买次数
- 白金币 / 日
- 预计累计白金币
- 是否被类别上限卡住

用户可以据此自己决定是否值得花白金币。

## 12. 目标天数规划（额外功能）

“目标天数规划”不能和常规培养策略设置同时存在。

交互：

1. 编辑态左侧提供按钮 `按目标天数规划`。
2. 点击后，常规培养策略 / 推荐偏好暂时隐藏。
3. 用户指定目标天数。
4. 系统反推最低额外体力和最低购买次数。
5. 展示每日白金币、累计白金币、可行性。
6. 退出后恢复常规策略。

如果 8 次 / 日仍无法在目标天数完成，应明确标记“在当前规则上限下不可完成”，而不是继续给出虚假的购买建议。

## 13. 清单排序的真实语义

### 整体完成模式

- 拖拽可以改变 UI 展示顺序。
- **不应该改变推荐计划**。

### 优先完成密探模式

- 拖拽顺序就是 optimizer 的 priority order。
- 重新排序后，从当前规划起点重新求解。
- 会影响：
  - 哪个密探先完成；
  - 每日不同层级历练的组合；
  - 某些阶段边界；
  - 单个密探 ETA。
- 通常不一定显著改变“整张清单全部完成”的理论最短时间，但可能因为为优先密探牺牲了部分全局效率而略微延长总 ETA。

## 14. 推荐算法伪代码

```text
state = initial_agent_shortages

for each date d:
    if d has manual planned override:
        plan[d] = planned[d]
    else:
        energy = base_energy
               + purchase_energy(preferences.purchase_count)
               + extra_gain[d]
               - dispatch_cost(preferences)

        plan[d] = solve_day(
            state,
            energy,
            strategy,
            agent_order,
            category_caps,
            action_costs,
            action_yields
        )

    state = apply_plan(state, plan[d])

    if all shortages == 0:
        ETA = d
        break
```

用户编辑日期 d 后：

```text
mark d as manual_override
replay all states up to d
for future dates:
    preserve manual overrides
    regenerate all non-manual recommendations
```

## 15. 仍需补齐的精确规则

以下三项是把 demo 升级为精确 optimizer 的关键缺口：

1. **每次购买体力恢复多少体力**。
2. **各类历练单次消耗多少体力**。
3. **兵书残卷 / 全卷分别对应多少经验值**。

建议额外确认：

4. 体力上限 / 自然恢复是否会因为满体而损失。
5. 邮箱储备、活动体力是否有领取期限。
6. 是否允许把当天剩余体力自然结转到下一天，还是应作为显式“储备体力”来源管理。

## 18. v13 demo 验收清单

最新完整 demo 应满足：

- 展示态显示紧凑密探清单。
- 编辑态密探清单可以拖拽，也可以用上下按钮调整顺序。
- “整体完成”模式下，排序只改变显示；“优先完成密探”模式下，排序参与重新规划。
- 购买体力次数在“推荐偏好”里由用户自己设置。
- 方案对比只存在于编辑态。
- 目标天数规划是额外按钮，进入后与常规策略互斥。
- 日期切换在展示态和编辑态均正常，但编辑态日期栏只属于右侧编辑区域。
- 任意日期新增 / 修改获取或支出后，该日标记为 manual override。
- 当天产出重新结算，后续 shortage 自动更新。
- 规划器每次加载、手动刷新或收到 `inventory_import` 事件时重新读取 `/v1/inventory/current`；当天库存快照是每次模拟的唯一库存起点。
- 规划器不调用 `/v1/inventory/acquired`；日期切换只改变模拟日期，不把推荐支出解释为真实流水。
- 未来无手工 override 的日期自动重新生成 recommended。
- 未来已有 manual override 的日期保留。
- 添加获取 / 支出使用菜单而不是 prompt。
- 今日方案 chip 样式沿用既定渠道色板。
- 页面底部提供完整配色色板与 demo 规则假设。
