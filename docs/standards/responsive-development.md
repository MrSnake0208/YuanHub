# YuanHub 响应式开发规范

> 本文是 YuanHub Web 前端在手机、平板与桌面端同步开发时的权威规范。
> 适用于所有新增或修改的页面、组件、布局、弹窗、导航、表格、工具栏与交互区域。
> 视觉风格继续以 [MaaYuan Share 设计规范](./design-system.md) 为准；本文只规定跨视口与跨输入方式的开发约束。

## 1. 核心目标

YuanHub 的 UI 功能不得以“桌面端看起来正常”作为完成标准。

任何涉及 UI 的新增或修改，都必须同时保证：

- 手机端、平板端、桌面端均可完成同一核心任务。
- 不依赖某一种屏幕尺寸、鼠标 hover 或固定高度才能使用。
- 在窄屏下优先调整信息层级和交互形式，而不是简单缩小桌面布局。
- 在宽屏下允许增强信息密度，但不得维护一套与移动端完全分叉的业务实现。
- 修改已有组件时，不得让已经可用的其它视口退化。

“响应式”是功能完成条件的一部分，不是功能完成后的补丁阶段。

## 2. 开发原则

### 2.1 Mobile First

新增样式优先从窄屏的基础布局开始，再通过更宽的可用空间增强。

推荐：

```css
.component {
  display: grid;
  grid-template-columns: 1fr;
}

@media (min-width: 768px) {
  .component {
    grid-template-columns: 280px minmax(0, 1fr);
  }
}
```

不推荐把桌面布局作为默认状态，再依赖大量 `max-width` 规则逐层“救火”。

已有页面不要求为遵守本文而一次性重写；但修改到的区域应优先向 Mobile First 收敛，且不得新增新的桌面优先技术债。

> 视觉尺寸、密度与组件外观不要求跨页面统一。当前明确设计方案决定按钮、标签、页头、圆角、间距与排版；未指定时沿用已有模块，不因响应式规范而给所有控件批量增加空白。

### 2.2 业务逻辑保持单源

不要因为手机和桌面布局不同而复制业务页面或状态逻辑。

优先：

- 同一个页面与状态源。
- 同一组业务组件。
- 根据可用空间切换排列、显隐层级、摘要方式或交互容器。

只有在信息结构本身明显不同的场景，才允许为同一数据提供桌面表格与移动卡片两种视图；二者必须共享同一数据、权限与操作逻辑。

### 2.3 断点由内容决定，不由设备型号决定

CSS 断点用于解决“内容在某个宽度开始放不下”的问题，而不是判断用户使用了哪一款手机或平板。

禁止把以下逻辑作为布局判断依据：

- iPhone / Android 型号。
- User-Agent 字符串。
- “小于某宽度一定是触屏设备”。

设备能力需要单独判断时，优先使用：

```css
@media (hover: hover) { }
@media (hover: none) { }
@media (pointer: fine) { }
@media (pointer: coarse) { }
```

### 2.4 组件优先响应自己的可用空间

可复用组件在不同页面中可能获得不同宽度。适合时优先使用 Flex/Grid、`minmax()`、`clamp()`、`min()`、`max()` 与 Container Queries，让组件根据自己的容器响应，而不是不断新增全局页面断点。

## 3. 验收视口与风险分级

CSS 断点不绑定设备。YuanHub 保留以下参考视口，但**完整矩阵不是每次 UI 小改动都必须执行的固定门禁**。

| 视口宽度 | 用途 | 必查重点 |
| --- | --- | --- |
| **320px** | 极窄手机下限 | 横向溢出、文字挤压、按钮可达性 |
| **390px** | 手机主基准 | 日常移动端布局、导航、表单、弹窗 |
| **430px** | 大手机 | 卡片扩展、工具栏换行、双列临界状态 |
| **768px** | 平板 / 中间态 | 布局切换、双栏、侧栏与内容关系 |
| **1024px** | 小桌面 / 平板横屏 | 导航、表格、密集工作区 |
| **1440px** | 桌面主基准 | 信息密度、最大内容宽度、宽屏留白 |

涉及全屏编辑器、底部操作栏、移动导航、复杂表单时，还应额外检查一次**手机横屏**。

按改动风险选择范围：

| 风险 | 典型改动 | 响应式验证范围 |
| --- | --- | --- |
| **L0** | 文案、颜色、图标替换、不会改变布局结构的间距/字号微调 | 不要求完整矩阵；确认没有引入明显换行/溢出风险即可 |
| **L1** | 单组件局部布局、按钮/卡片/工具栏微调 | 重点检查受影响视口，通常以 390px + 1440px 为基准 |
| **L2** | 组件断点切换、弹窗/Drawer、表格、复杂工具栏、sticky/fixed | 至少覆盖手机、平板/中间态、桌面，并检查真正发生布局切换的临界宽度 |
| **L3** | 新页面、导航、页面级结构、核心工作区、全屏交互 | 使用完整 320 / 390 / 430 / 768 / 1024 / 1440px 矩阵；必要时加手机横屏 |

如果当前任务明确由用户负责运行时回归，Agent 仍需按上表设计和实现响应式行为，但不必自行逐个启动浏览器视口；最终汇报列出需要用户验证的视口即可。

## 4. 页面与布局硬约束

### 4.1 禁止页面级横向溢出

普通页面在 320px 下不得因为布局错误出现整页横向滚动。

常见要求：

- Flex/Grid 子项需要时设置 `min-width: 0`。
- 图片、视频、画布等不得超出容器，按场景使用 `max-width: 100%`。
- 长 ID、版本号、URL、用户输入文本应使用合理的换行、截断或可复制详情。
- 固定宽度只能用于明确不会超出容器的局部元素。

不要用根节点 `overflow-x: hidden` 掩盖未知溢出源；应先修复真正超宽的组件。

### 4.2 内容宽度与间距

- 页面主体使用流式宽度与合理的 `max-width`，不要把桌面固定像素宽度直接带到手机。
- 横向 gutter 随可用空间调整；窄屏优先保证内容可读和操作可点。
- Grid/Flex 中承载正文、标签、输入框、表格的列通常应使用 `minmax(0, 1fr)` 或等价约束。
- 不通过无限缩小字体来“塞下”桌面内容。

## 5. 常见组件的响应式规则

### 5.1 导航与侧栏

桌面可使用 Sidebar + Content；窄屏应切换为顶部入口、Drawer、底部导航或项目现有的移动导航模式。

要求：

- 移动端不能保留一条被压到只剩图标或被裁切的桌面侧栏。
- 当前页面、返回、主要模块入口必须明确。
- 固定导航不得遮挡页面首尾内容。

桌面宽度 ≥1081px 且高度 ≤480px 时，`IslandSidebar.vue` 使用整座侧栏内部滚动，品牌、主导航和账号区不再争抢固定高度；“更多”在流内展开，避免上弹进入更新提示条覆盖区。更高的桌面窗口仍保持主导航独立滚动，手机抽屉保持头尾固定、中间导航滚动。可在已运行的开发服务上做精确布局检查（公开反馈广场 + 合成更新条，不代表登录业务页或原生 iOS 验收）：

```bash
npx --no-install playwright cli -s=sidebar-reachability open http://127.0.0.1:5173/feedback/plaza --browser=chrome
npx --no-install playwright cli -s=sidebar-reachability run-code --filename=test-support/sidebarReachability.browser.js
npx --no-install playwright cli -s=sidebar-reachability close
```

### 5.2 表格与密集数据

不要默认把宽表硬压进手机。

按数据特性选择：

1. 移动端卡片视图；
2. 保留关键列，其余进入详情/展开区域；
3. 只有横向对比本身不可替代时，才使用局部横向滚动容器。

禁止因为一张表导致整个页面横向滚动。

桌面表格与移动卡片并存时，必须复用同一数据源、过滤条件、权限判断与操作函数。

### 5.3 工具栏与筛选

桌面端可平铺搜索、筛选、排序和批量操作；窄屏应允许：

- 换行；
- 合并为“筛选 / 排序 / 更多”；
- 抽屉或弹层承载低频选项。

核心操作不能因为空间不足直接消失。

### 5.4 Modal / Drawer / 编辑面板

桌面弹窗可居中并限制最大宽度；手机端优先使用接近全屏、Bottom Sheet 或紧凑全屏编辑器。

要求：

- 高度使用动态视口单位，例如 `dvh`，避免把裸 `100vh` 作为移动端全屏方案。
- 长内容区域独立滚动。
- 重要提交/保存操作在长表单中保持可达。
- 打开软键盘后，当前输入与主要操作不得被永久遮挡。
- 关闭按钮与主要动作需要足够触控区域。

### 5.5 Sticky / Fixed 元素

所有固定在顶部或底部的元素都必须同时检查：

- 是否挡住滚动内容；
- 是否与其它 sticky 元素叠加；
- iOS 安全区域；
- 软键盘出现后的可达性。

底部固定 UI 按场景使用：

```css
padding-bottom: calc(12px + env(safe-area-inset-bottom));
```

全屏或贴边布局还需根据需要处理 top / left / right safe area。

### 5.6 图片与媒体

- 图片默认不得撑破容器。
- 卡片内图片明确 `object-fit` 行为。
- 不为了桌面大图在手机端保留固定宽高。
- 对性能敏感的大图保持项目既有懒加载与压缩策略。

## 6. 交互与输入方式

### 6.1 不允许 Hover-only 功能

Hover 可以提供增强反馈，但核心操作不能只在 hover 时出现。

在 `hover: none` / `pointer: coarse` 环境下必须仍然能：

- 看见或发现主要操作；
- 打开详情；
- 完成编辑、保存、删除等任务；
- 理解当前选中/展开状态。

### 6.2 触控目标

YuanHub **不设置全站统一的 44×44 CSS px 最小点击区域，也不强制统一按钮高度**。按页面用途、信息密度、操作风险、鼠标或触控输入，以及本次具体设计来决定视觉尺寸和实际命中区；不要为了凑固定尺寸机械放大筛选标签、图标和工具栏。

交互目标仍应清晰可辨、可操作，且不应相互覆盖或容易误触。必要时可针对性扩大命中区、调整间隔或交互形式，不必同步放大视觉图标；遵循适用的网页无障碍要求与目标尺寸例外，不用单一像素值作为全站通过标准。

### 6.3 键盘与焦点

响应式改造不得破坏：

- Tab 顺序；
- `:focus-visible`；
- Esc 关闭弹层（适用时）；
- 焦点不被 sticky header/footer 长期遮挡。

## 7. 移动浏览器专项

### 7.1 动态视口高度

移动端全屏容器优先考虑：

- `100dvh`：跟随动态浏览器 UI；
- `100svh`：需要稳定“小视口”时；
- `min()` / `max()` / `calc()`：配合页面 chrome。

不要新增依赖裸 `100vh` 的关键全屏交互。

### 7.2 Safe Area

对于贴边的顶部栏、底部栏、Drawer、全屏 Modal，按需要使用：

- `env(safe-area-inset-top)`
- `env(safe-area-inset-right)`
- `env(safe-area-inset-bottom)`
- `env(safe-area-inset-left)`

### 7.3 软键盘与 Visual Viewport

只有当固定面板、浮层定位或输入体验确实需要时才监听 `visualViewport`。监听必须有清理逻辑，不要为普通布局引入 JS 尺寸同步。

能用 CSS 正确完成的响应式布局，不使用 JS 监听窗口尺寸替代 CSS。

### 7.4 iOS 输入聚焦缩放

`src/styles/main.css` 在支持 `-webkit-touch-callout` 的 iOS WebKit 中，为文本类 `input`、`textarea`、原生 `select` 和可编辑根节点设置至少 16px 的计算字号。规则在聚焦前生效，不依赖屏幕宽度，覆盖横屏、平板及 Teleport 弹层；`!important` 用于抵抗组件 scoped 样式和 `font` 简写。复选框、滑块、按钮等非文本输入不受影响。

需要大于 16px 的输入使用局部 `--input-font-size`，同时以该变量设置原有 `font-size` / `font`，保留其它平台字号。不要将此变量设到非输入祖先上，以免影响嵌套控件。普通正文、标题、只读富文本保持原有样式。

不得通过 viewport 的 `user-scalable=no` / `maximum-scale=1` 或手动重置缩放来规避问题。真实 iPhone Safari 复测：依次打开登录邮箱/密码、作业搜索、账房数字输入、反馈编辑及弹窗中的输入；记录聚焦前、聚焦后、收起键盘后的 `visualViewport.scale` 和 `height`，确认字号至少 16px、scale 不因聚焦变化、没有横向溢出，并确认双指缩放与页面滚动可用。桌面浏览器模拟不能证明 iOS 软键盘行为。

已有开发服务运行且 Playwright CLI 可用时，可运行以下字号回归。脚本使用真实登录输入、组件 scoped 样式和 body 下的弹层样本；Chromium 中会明确展开 iOS 规则，仅验证级联、计算字号、聚焦/失焦和溢出，不验证系统键盘或缩放。

```bash
playwright-cli -s=input-zoom open http://127.0.0.1:5173/login --browser=chrome
playwright-cli -s=input-zoom run-code --filename=test-support/inputFocusZoom.browser.js
playwright-cli -s=input-zoom close
```

## 8. Definition of Done

所有 UI 改动都要满足与本次修改**直接相关**的跨视口不变量，但验证范围按第 3 节风险分级执行。只有 L3 结构性改动默认要求逐项检查完整视口矩阵。

适用时确认：

- [ ] 手机宽度下无页面级横向溢出，核心内容不被裁掉。
- [ ] 390px 手机主流程或受影响组件可用。
- [ ] 受影响的断点临界宽度没有尴尬换行、遮挡或状态跳变。
- [ ] 中间态布局不会出现桌面/手机样式互相覆盖。
- [ ] 1440px 桌面布局与信息密度正常。
- [ ] 重要功能不依赖 hover。
- [ ] 控件在相关输入方式下可识别、可点击，相邻操作不明显误触；没有为统一像素尺寸牺牲信息密度。
- [ ] Modal / Drawer / sticky / fixed 元素不会遮住关键内容。
- [ ] 移动全屏 UI 已考虑 `dvh` 与 Safe Area。
- [ ] 表格与密集工具栏在手机端有明确降级方案。
- [ ] 内容放大、较长中文、长账号名/ID 不会直接撑爆布局。
- [ ] 修改没有复制出第二套业务状态或权限逻辑。

如果某项不适用于本次改动，无需为了“打勾”专门验证；在需要说明时写清不适用原因即可。

## 9. AI / 开发者工作流

### 开始修改前

1. 读取 `docs/standards/design-system.md`。
2. 读取本文 `docs/standards/responsive-development.md`。
3. 判断本次 UI 改动属于 L0–L3 哪一档。
4. 涉及页面新增或结构调整时，再读取 `docs/standards/page-development.md`。
5. 只有当布局/信息层级实际受影响时，才需要提前比较 390px 与 1440px 的差异。
6. 复用必要的业务数据、权限和操作逻辑；可按页面目标采用不同的桌面/移动视图与控件表现，不为外观统一复制或改写既有工作流。

### 开发过程中

对 L1 及以上布局改动，同时考虑 390px 与 1440px 两个基准，不允许“先把 PC 做完再补手机”。L0 文案/视觉修改不要求为了流程完整性额外启动两个视口。

出现窄屏问题时优先按顺序处理：

1. 信息优先级；
2. 布局重排；
3. 允许换行 / 折叠 / 展开；
4. 局部滚动；
5. 最后才考虑隐藏次要信息。

### 提交 / 发版前

按第 3 节的风险分级选择视口范围。新页面、导航、页面级结构和关键响应式交互使用完整矩阵；普通局部 UI 修改只检查与改动相关的基准/临界视口。重要版本再使用至少一台真实手机浏览器抽查动态地址栏、软键盘、触控和 Safe Area。

## 10. 旧页面处理原则

本文从加入仓库之日起作为新增和修改 UI 的长期标准。

对于已有页面：

- 不要求一次性全量重构。
- 未触碰区域可以保持现状。
- 本次修改涉及的组件和相邻布局不得继续新增明显的响应式技术债。
- 一旦发现旧实现会直接阻碍本次功能在手机/平板/桌面使用，应在本次改动范围内一起修复，或明确记录后续项。

目标是让 YuanHub 的响应式质量随着每次迭代单向改善，而不是反复在 PC 与手机之间回归。
