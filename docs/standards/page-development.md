# YuanHub 页面开发与玩家体验规范

本文是 YuanHub 页面开发、任务导向交互与玩家体验的唯一权威规范，适用于新增或修改的页面、表单、弹窗、交互和提示文案。纯后端且不影响用户交互的任务不触发整套 UI 流程。

先设计用户完成任务的方式，再安排组件和字段。普通页面面向玩家；管理后台、开发者文档和批量工具按实际使用者保留必要的专业信息与能力。业务正确、权限、账号隔离和数据安全优先，清晰、可访问、可操作仍是交付要求。

## 1. 基本流程

涉及 UI 时读取并应用实际可用的 `ui-ux-pro-max`；不可用时如实说明，不伪称已加载。按当前任务检索相关指导，不为局部修改生成第二套设计系统，不把 Skill 的原生 App 尺寸、图标库或样式建议套用为本项目 Web 硬约束。

新页面、功能扩展或流程变化先完成第 6 节的简短交互说明；目标与授权范围明确后自行继续，不增加固定等待审批的关卡。文案、图标、局部样式等小改动只明确范围，不要求长方案、永久文档或 Trellis task。任务生命周期与验证仍服从适用的 `AGENTS.md`，不默认新增全量测试、截图基线、审计平台或多 Agent 流程。

新建页面的工程接入步骤：

1. 在 `YuanHub/src/pages/<模块>/` 下创建页面 `.vue` 文件。
2. 在 `YuanHub/src/router/routes.js` 中按照现有路由模板注册页面。

页面视觉优先按本次明确的设计稿或提示词实现；[MaaYuan Share 设计规范](./design-system.md) 提供现有品牌和样式参考，不要求所有页面外观统一。跨视口可用性、业务逻辑复用与可访问性仍遵守 [YuanHub 响应式开发规范](./responsive-development.md)。

优先继承实际主题、token、公共组件及既定 PC/Mobile 展示架构。参考图只决定视觉方向，不能决定游戏道具、奖励、数量、日期或 API 语义；这些须核对真实项目目录、配置和业务规范。演示数据与正式数据分离。没有明确授权，不修改导航、全站主题、字体或图标体系，不顺带重做其他页面。

任何页面不得以桌面端完成作为交付标准。按响应式规范的风险等级考虑相关手机、平板和桌面视口；完整矩阵仅用于结构性高风险 UI 变更。仓库浏览器自动化默认禁用，真实布局与触控由用户手动验收，除非本次明确授权。

## 2. 页面目录

页面统一放在：

```text
YuanHub/src/pages/<模块>/
```

现有示例包括：

- `YuanHub/src/pages/today/index.vue`
- `YuanHub/src/pages/work/index.vue`
- `YuanHub/src/pages/work/detail.vue`
- `YuanHub/src/pages/tools/cart.vue`

例如材料价值页可放在：

```text
YuanHub/src/pages/material/value.vue
```

## 3. 路由注册

路由结构保持现有拆分：

- `YuanHub/src/router/routes.js`：路由表与顶部注释模板。
- `YuanHub/src/router/index.js`：创建路由实例并导入 `routes`。

新增页面时，在 `routes.js` 中按现有模板填写需要的 `path`、`text`、`name`、`display`、`module`、`icon`、`component`、`meta` 等字段。

## 4. 页面文件示例

```vue
<template>
  <button class="page-demo-button" type="button" @click="data = '111111'">
    {{ data || '更新' }}
  </button>
</template>

<script setup>
import { ref } from 'vue'

const data = ref('')
</script>

<style scoped>
.page-demo-button {
  padding: 8px 12px; /* 示例仅展示局部样式，不规定全站按钮尺寸 */
}
</style>
```

示例只说明页面文件与 Vue 3 `<script setup>` 的基本形态；具体视觉由本次设计要求决定，现有组件与设计规范作为参考，避免为外观统一复制非必要结构。

## 5. 变更检查

按实际改动确认，不把无关项变成固定门禁：

- 新页面位于 `src/pages/<模块>/`，在 `src/router/routes.js` 注册，不另建路由体系。
- 视觉按本次明确要求与 `design-system.md` 实现，响应式遵守 `responsive-development.md`，两端共享业务状态、权限与 API 逻辑。
- 新页面、功能扩展或流程变化已说明使用者、默认内容、次级路径、保留能力及关键状态；功能扩展还须说明页面保护与界面净变化，文案或局部样式小修无需新方案。
- 验证范围按风险选择；视口以 `responsive-development.md` 第 3 节为准，完整矩阵仅用于结构性高风险 UI 变化。实际页面验收与未验证项按第 11 节记录。

## 6. 开发前的交互说明与增量设计

### 6.1 默认扩展现有任务，不顺手重设计

新增或扩展能力，包括一次提出的一批需求，默认属于**增量设计**：沿用所在页面的职责、主要布局与交互模式，只改承接新任务所必需的区域。增加功能不自动授权重排全部模块、改变导航、替换全站主题或重做其它页面。确需结构调整时，先说明原因、影响和取舍；授权范围内可继续实施，超出范围的重设计不得夹带执行。局部必要调整不设固定审批关卡。

先查本次需求、相关源码和已有明确认可的设计/截图，区分“当前实现”“已验收基准”“概念参考”；没有真实验收证据就标记未验证，不把生成图、旧代码或自己的审美当作已验收结论，也不为建立基准自动运行浏览器。明确本次要保护的旧主任务、完整有效信息、账号上下文，以及相关筛选、草稿、返回位置与键盘操作；保护可用体验，不冻结像素或阻止授权范围内修复旧问题。

一批需求先按玩家任务合并，再决定入口与状态，不能按照需求条目逐项追加卡片、Tab、说明区或表单。频率和使用场景没有证据时标为设计假设，不编造用户数据；不因需求数量多就扩大主页面常驻面积。

### 6.2 一份简短说明

新页面、新表单、功能扩展或流程变化，在实现前简述以下内容；留在当前对话或已有任务即可。沿用成熟模式的局部扩展可合并为几句话，不另建长期文档、审批流程或第二份方案。小文案、图标、局部样式修改只明确范围。

```text
任务与类型：谁使用、主要做什么；局部扩展还是已授权的重设计。
现状与保护：参考来源与未验证项；不能退化的旧任务、信息与上下文。
最短路径：新任务及受影响旧任务如何进入、操作、完成和返回。
功能归属：这批需求如何合并；默认可见、对象操作、情境操作或次级管理入口。
界面净变化：常驻模块/控件新增、移除或迁移了什么；主体位置、输入/步骤和手机呈现的变化及理由。
数据与边界：真实数据来源、保留能力、允许变更范围及写入影响。
状态与验证：相关状态、视口与错误恢复；新旧路径的检查方式和待验收项。
```

说明必须解释用户为什么来、如何完成、失败后怎么办，不能只列卡片、圆角和配色。净变化不能只写“保持简洁”：没有新增常驻内容也应简述入口在哪里；若增加常驻区、默认输入或操作步骤，要交代必要性与对旧任务的影响。非关键可逆细节沿用现有模式；无法可靠判断且会改变真实数据的关键事实，先消除歧义再写入。

### 6.3 按任务选择入口，控制默认负担

| 功能归属 | 优先承接方式 | 防止的退化 |
| --- | --- | --- |
| 当前主任务的延伸 | 融入现有操作或编辑流程 | 不为每个新增能力再放一张常驻大卡片或重复入口 |
| 针对某个对象 | 在对象附近提供清晰操作，必要时用有名称的菜单 | 不把对象操作提升为全页工具栏；不能仅靠 hover 或无提示手势发现 |
| 选中、编辑或特定状态才需要 | 进入相应状态后显示操作，入口与退出路径可发现 | 不让批量操作常驻挤压浏览，不让切换状态丢草稿或选择 |
| 长期配置、历史补记或低频管理 | 进入对应的设置/管理流程，完成后返回原任务 | 不每天重复填写配置；不把所有能力无差别塞进“更多”或嵌套弹窗 |
| 真正独立、较长的任务 | 有依据地采用专用工作区、视图或页面 | 不按 API/字段数量拆 Tab；需要同时对照的信息不强行分离 |

默认负担不要求机械“零增长”，完整内容也可以自然变长；必要的新入口或状态应保留。常用操作、关键错误、风险与必要确认不得为了清爽隐藏，不用缩字号、裁切内容或取消能力换取首屏整齐。菜单/弹层沿用可访问名称、可见焦点、焦点恢复和跨视口可操作性，不把原生 App 尺寸硬套给 Web。

先检查现有组件和交互模式是否适用；复用成熟行为，不强制全站外观一致，也不新建巨型通用页面组件。旧模式不适用时在本次授权范围内局部替换，并交代原有能力的去向。

## 7. 字段按任务分层

系统有字段不等于界面要有输入框。新增或重组表单时按以下分类；简单修改不要求输出分类表。

| 字段类型 | 呈现与处理 |
| --- | --- |
| 必要输入 | 当前任务不可缺少且系统无法可靠判断的内容，在当前步骤显示，标签与单位明确 |
| 可靠默认 | 已有可靠数据或确定计算结果自动带入，必要时允许查看和更正，不要求重复填 |
| 长期配置 | 常用偏好放配置入口，按适当用户/账号范围记住，区分“仅本次”和“以后默认” |
| 情境设置 | 补记、批量、特殊情况进入对应任务或满足条件时再显示，入口可发现 |
| 内部字段 | 不进入普通玩家流程，必要影响翻译成玩家能理解的结果；专业工具按实际任务保留 |

不猜测真实行为，不把未知当零，不把关键风险和必要确认藏进“更多”。配置了月卡不代表今天已领取；未选择的奖励不能自动按已领取提交。

## 8. 主体、能力与操作负担

每个页面明确主任务或主内容，辅助录入、配置和历史为它服务。库存的主体是完整分类库存：保留分类、道具、数量和必要折算，不能只留下少数摘要卡，或让全部资源都需要额外寻找。完整内容可以自然变长，不为首屏高度隐藏重要信息。

常用内容直接可见，低频配置按需出现。常用动作通常保留一个易发现的入口；移动端固定操作区等必要重复须共享同一语义和数据处理。零数据只需紧凑摘要、下一步与管理入口，不用大表单、大幅插画或长篇教学挤走主体。

保护既有数据、业务规则、持久化、账号隔离和仍需使用的能力；旧输入框排列、弹窗层级与组件边界不是必须保留的契约。旧组件不适合新任务时，可在授权范围内复用业务服务、拆开数据逻辑并替换展示；不能只换卡片或把旧管理表单塞进折叠区就宣称减轻负担。

一次用户动作应有连贯流程和明确结果。邮件领取、兑换等多项数据变化需核实底层一致性，前端合并按钮不能证明后台不会部分成功。数量更新与获得统计分开；未填写项不得归零；历史补记按已核实的时间与覆盖关系处理，不一律重复加库存。有歧义时作最小必要询问；缺少底层能力时说明依赖，不能用隐藏按钮或虚假成功掩盖。

## 9. 状态、反馈与文案

按需覆盖默认、展开、零数据、加载和失败；异步录入明确正常、处理中、成功与失败，有已完成、部分选择、编辑状态时追加，不强制构造全部组合。

- **真实状态：** 未知不是零，读取失败不是空列表或“今天尚未记录”。状态不只靠颜色，选择、完成、禁用和错误都有可理解的语义。
- **提交与恢复：** 提交有反馈并防止误重复，只禁用相关操作；保留安全的查看、取消和退出路径。失败保留可恢复输入、关联字段错误及下一步，不把堆栈或内部枚举交给玩家。
- **完成与保护：** 成功说明实际变化，必要时列受影响项目。保存、取消或关闭后合理保留筛选、滚动与焦点；确有未保存内容丢失风险才提示。删除、覆盖保留必要确认，可撤销操作优先提供恢复入口。
- **动作与信息：** 按钮描述“记录领取”“更新数量”等任务，避免内部算法词汇；保留名称、单位、计算口径和风险提示。删除重复标题与说明，低频规则放相关任务或帮助入口；标签不能仅靠 placeholder，不可用操作应说明原因。
- **可读与可操作：** 紧凑靠减少重复和寻找，不靠缩字号或触控范围。不得用巨大标题、banner、空白或全局裁切遮盖信息和布局问题；长中文、数字与单位不能挤成意外竖排。收缩、换行、局部滚动、焦点及弹层遵守既有响应式和设计规范，不机械禁止所有最小高度。

## 10. 库存案例：纸面规则演练

以下是期望交互，**不是对现有代码能力或页面实现的确认**。只在相关任务中应用，不触发旧页面返工。

批量扩展演练：月卡设置、邮件管理、历史补记与批量更新不应各变成默认展开的表单。分别检查是否能由对应奖励的设置入口、邮件摘要的管理入口、录入流程的补记分支、库存编辑状态承接。保护完整库存总览和常用录入路径，逐项说明界面净变化；这是归属示例，不代表这些能力尚未实现，也不授权删除现有入口或重做库存。

| 场景 | 应显示 | 不常驻/不推断 | 访问路径 | 人工验收要点 |
| --- | --- | --- | --- | --- |
| 普通奖励记录 | 真实配置、领取状态、实际已领项目选择与保存结果 | 长期档位与默认时间不每天重填；不默认勾选已领；不要求理解“加库存/只补历史” | 库存中的常用奖励记录入口；长期配置、补记与纠错有独立可发现入口 | 无改配置也能记录；仅确认项目生效，未选择不写入；展开配置可达，仅本次修改不暗改以后默认；处理中与失败可辨，失败保留输入 |
| 邮件为零 | 读取成功后显示零封紧凑摘要和管理入口，完整库存仍可见 | 不常驻大型封数表单或无用的领取/保存按钮；加载、失败不能冒充零封 | 邮件摘要旁的管理入口 | 真零封可管理；加载显示处理中，失败显示恢复路径；主体不被零封表单占据 |
| 管理邮件 | 管理任务中显示真实封数/奖励、必要编辑与结果；领取是连贯动作并说明库存影响 | 管理字段不常驻普通路径；不让用户先减封数再跨页面加背包；不预设底层已有原子能力 | 从邮件摘要进入管理，完成或取消后回到库存原位置 | 可完成管理并返回；取消不写入；如包含领取，核实邮件与库存一致、重复提交不重复入库，部分失败明确可恢复；能力缺口标未完成 |
| 完整库存总览 | 分类、道具、数量、必要折算为主体，常用动作清晰 | 不以几张常用资源卡替代完整信息，不把全部库存推到多个额外入口 | 库存主内容区；录入、配置和历史作为辅助入口 | 无需先打开录入才能看完整库存；桌面/手机都能浏览分类与数量，辅助区不挤走主体；编辑只改确认项目并保留位置 |

真实验收使用合适的开发/测试数据；先核实具体能力、数据来源和写入边界，再执行涉及数据的路径。不得把纸面演练或代码推断写成“库存已实现/验收通过”。

## 11. 按风险交付与维护

### 11.1 验证责任与范围

遵守适用的 `AGENTS.md`；在 YuanHub-All 内同时遵守工作区 `TESTING.md`，独立开发以本仓库风险策略为准。L0/L1 以相关文件与 diff 自检为默认，不强制测试或构建；L2 只为明确回归风险选择定向检查；权限、账号隔离、数据损坏、持久化、事务等 L3/L4 关键约束必须取得可复核的定向证据，不能全推给后续验收。涉及库存增减、兑换、覆盖导入时，按风险验证重复提交、覆盖关系、部分失败和账号边界，优先复用现有测试。

真实页面、触控和运行时交互默认由**用户手动验收**。Agent 提供页面、操作、预期与建议视口；只有当前任务明确授权浏览器自动化，才可在授权范围内使用已有工具走查或截图，不因此启动、重启或停止现有服务。普通“测试/验证”不包含浏览器授权。未有实际证据时，写明“视觉/交互未验证”，无需固定等待用户审批才能交付本地实现。

普通局部交互可建议 390px 与 1440px，涉及布局切换补查 768px 或实际临界宽度；结构性高风险改动仍按 `responsive-development.md` 第 3 节的完整矩阵，不用本例样本降低既有要求。默认、相关展开、零数据、加载与失败按实际影响选择，修复过的竖排、空白、溢出须在原状态复查。小文案/样式改动不要求额外跑整套状态与视口。

工程风险与体验影响分别判断：改动行数少不代表不会挤走主内容，但体验检查也不自动升级为全量测试。功能扩展应覆盖新任务和直接受影响的旧任务，关注入口可发现、必要信息完整、无理由新增的输入/步骤，以及完成/取消后的上下文保留；不要求每次全站巡检。默认态正常不能替代相关展开态的检查，检查方式仍遵守上文授权与风险边界。

### 11.2 轻量验收记录

记录留在交付说明或已有任务中，不强制另建报告；小改动可用几句话。**功能实现与体验验收分开陈述**：代码已完成可以交付人工验收，但不能据此宣称整体页面体验合格，也不因等待人工验收增加固定审批门槛。

```text
范围与实现：实际变更的页面/组件、能力和边界。
界面净变化：实际新增/移除/迁移的常驻内容，是否偏离事先说明及原因。
新旧路径：新任务与直接受影响旧任务的操作、结果；纸面推演与实际走查分开。
状态/视口：实际检查的状态与宽度；待用户手动检查项另列。
证据与数据：真实检查结果/截图来源、相关数据验证；无证据或不涉及须明确。
体验与限制：已验收、待人工验收或存在已知问题；未验证项、阻塞与剩余风险。
```

用户另行安排 DSH 时，以原始需求、页面保护约定和最终变更独立检查，不只照抄开发者的成功路径；尤其检查不依赖开发说明是否能找到新入口、旧任务是否变难。保留原有浏览器授权与角色分离规则。一次性问题留在任务中，只有反复出现且可复用的经验才更新公共规范。

构建、静态检查、jsdom、示意图与截图各有边界：构建不能证明布局，截图不能证明交互或数据正确。无真实页面检查，不得宣称视觉/交互验收通过。主要任务无法完成、能力丢失、重复加数量、跨账号串数据、覆盖误清零或虚假成功须修复或明确标记未完成；明显竖排、裁切、遮挡、大块无用空白不得通过换一张截图回避。设置被藏到无法发现或普通路径仍需解释内部算法时，重做任务分层。

### 11.3 单源维护
