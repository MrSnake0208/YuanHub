# 库存页面快捷维护

库存页以完整分类总览为主体。资源道具、密探养成材料、属性分组、心纸、折算信息、分类顺序和分类编辑保持原数据来源；首次使用也直接展示目录，不需要先展开「全部资源」。

## 玩家操作

1. **今日奖励**：勾选实际领取的每日茱萸、密探日常、月卡奖励，点击「记录今日领取」。数量来自现有奖励配置，月卡档位读取当前账号的养成规划设置；「调整奖励」可改本次数量，也可前往原有长期配置。
2. **记一笔**：默认「获得」，选道具、填数量、保存。支持多道具；来源、派遣/历练、心纸、历史时间仍在可展开的设置中。使用与兑换沿用现有符传命令及固定游戏价格，不新增任意道具负数导入协议。
3. **更新数量**：直接输入当前实际数量。分类「编辑」仅提交本分类的局部更新；顶部入口用于跨分类维护。完整首次盘点仍需明确确认，未修改的既有数量保留。
4. **邮件**：「管理邮件」维护未领取的月卡储备；「记录邮件领取」确认本次刚领取全部已保存邮件，同时清空待领封数并记入库存。部分领取继续通过「记一笔」及管理剩余封数处理。已经记录或包含在当前数量中的邮件，不得按新领取再次提交。
5. **最近记录**：打开原操作历史工作区，保留原有查询、删除、撤销和报告导入；统计报告继续可用。

## 数据边界

- 日常快捷区复用 `dailyRewardRecordId`，与原日常入口共用来源/游戏日标识。游戏日按北京时间 05:00 划分；已记录项目不可再次勾选。
- 补记已包含在库存中的日常奖励时，选择「已计入当前数量，只补记录」，填写真实领取时间；仍由 `validateDailyAnnotation` 和后端 full/listed 基准决定是否只保存历史。
- 任意来源手工记录与无来源日期的聚合邮件储备，不能自动推断是否为同一笔游戏奖励；界面要求玩家核对是否已记录，不按相同数量猜测或合并。
- 写入结果不明时保留原文档/操作编号，禁止换账号、修改内容或生成新编号绕过重试。账号/身份变化与卸载后忽略迟到响应。

## 邮件联合领取接口

站内 JWT：`POST /v1/inventory/mailbox-reserve/claim?account_id=<当前账号>`。

正文严格为 `{ "expected_version": 1, "operation_id": "稳定操作编号" }`；不接受用户身份、客户端奖励金额、价格或发生时间。响应沿用 `MailboxReserveResponse`，禁止缓存。

后端从账号已保存储备计算白金币和普通符传（每封 3 张），使用现有 Hub Mongo 事务完成储备版本 CAS、奖励导入、当前库存和库存 revision 更新；不增加集合、索引或迁移。服务端当前时间作为刚领取时间，仍尊重更晚库存基准。记录 ID 为 `yuanhub:mail:<储备版本>:<操作编号>`，重复请求只返回当前储备；删除后的领取只能从原历史记录显式恢复。单笔奖励不能超过现有库存协议上限。

此接口需要前后端同时更新；旧后端不具备联合领取能力。不得用两个互不原子的前端请求替代。

## 手动界面验收

- 桌面约 1440px：完整分类持续可见，快捷区横排，普通获得无需预览确认；分类编辑只显示对应道具。
- 手机约 390px，并补看 320px：三个入口和奖励选项自然重排，无整页横向溢出；数字输入、软键盘、弹窗滚动及保存按钮可达。
- 真实视觉、触控与浏览器兼容性由用户手动检查；组件/事务测试不能证明上述运行时表现。
