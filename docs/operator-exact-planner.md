# 体力日程全局最优计算

日程首页保留快速推荐，并提供「可进入编辑日程界面计算全局最优解」入口。编辑界面点击计算后才加载本仓库的 HiGHS WebAssembly 求解器，在独立 Worker 中运行；可选 30、60、120 秒，可随时取消。普通日程先预览，点击「采用此方案」才保存。

每日获取或支出的编辑仍只更新账本并提示可重算，不会自行启动全局求解。全局计算从所选日期的材料缺口开始，保留当天全部体力获取、派遣、自定义支出及未来手工日，重新安排当天全部历练与 6-24，以及后续自动日程。采用时保留此前日期。输入、日期或账号变化会取消旧任务并使旧结果失效。

## 优化目标与证明

- **整体最快**：以逐日整数刷取次数建模，用可行性二分搜索证明全部材料最早备齐的天数。
- **按清单优先**：依清单顺序逐一最小化各密探的备齐日期，固定已经证明的日期后优化下一位。不同材料的后排密探可以更早备齐；共享材料按清单顺序分配。
- **目标天数**：独立试算期限内最低累计白金币，联合选择每天 0–8 次购买及刷取安排，不改写已保存日程。固定派遣超过免费体力时比较不同完成期限，避免在材料备齐后继续计入不必要的购买。

模型包含每日体力预算、各历练每日次数上限、已解锁关卡、固定产出和逐材料需求约束。材料库存沿用现有结算规则，仅抵扣一次。仅在同一每日次数限制内移除被其他关卡完全覆盖的选项，不把不限次数的 6-24 与有限次经验历练合并。

「全局最优」限定于当前确定性产出、无跨日体力结转、固定体力获取与购买设置等项目规则，以及最多 90 天的规划范围；不代表覆盖游戏中尚未建模的随机收益或额外渠道。普通模式计算最短天数，白金币模式才优化购买成本。

HiGHS 的最优间隙设为零；每个候选方案还会通过现有日程结算器独立复核整数次数、预算、产出及完成日期。只有完成证明才显示最优：超时但已有合法方案显示「已有可行方案，尚未证明最优」；未找到方案显示无法判断；仅求解器证明不可行时显示期限不可行。最短日期证明后的体力消耗择优步骤超时，不影响已经成立的日期证明。

## 保存与运行资源

采用结果的证明信息存于 `schedule.result.optimization`，包含状态、目标、起算日期、完成天数、范围和求解器版本。修改日程会移除此信息，防止继续展示过期证明。待重算提示仍存于 `context.planBaselines`。云端沿用现有日程状态和嵌套元数据，不增加顶层协议字段。

运行资源固定于 `public/solver/highs-1.15.3/`，包含原始 MIT 许可与来源说明，无运行时 CDN 或仓库外依赖。WASM 约 3.5 MB，仅点击计算后请求；不会纳入现有 PWA 的 JS/CSS/HTML 预缓存匹配范围。

相关实现：`src/data/exactPlanner.js`、`src/data/exactPlannerRunner.js`、`src/workers/exactPlanner.worker.js`、`src/components/operator/PlannerExactOptimizer.vue`。

最短日期求解结束后，推荐日剩余体力按每次 10 点补入 6-24，额外经验计入结余库存；不足一次的体力保留。该步骤不增加购买，不改变未来手工日，也不向材料备齐后的日期追加支出。最短日期证明仍然成立。

## 方案对比层级

编辑界面按「规划条件 → 方案对比 → 每日执行」排列。培养策略、体力偏好和可刷层数属于规划条件；目标天数是独立试算模式，目标为期限内最低白金币，不与清单优先策略混用。

方案对比同时容纳快速估算和全局求解。点击一次计算后，依次求解零额外投入、每日购买两次，以及不重复的当前购买档位；每项具有独立时限和证明状态。目标天数模式展示零购买、两次购买及期限内最低白金币三个结果。为控制内存和 CPU 占用，Worker 每次运行一个方案；取消会停止剩余任务，已完成结果保留，输入变化则全部失效。

所有对比使用同一库存、所选日期和手工日约束。普通对比仅替换所选日及后续自动日的购买次数，所选日其他获取保持不变；未来手工日连同购买次数保持固定，因此「零额外投入」仍可能包含手工日既有费用。采用时同步保存所选购买偏好、首日方案与后续日程。账号或清单切换也会使结果失效，即使材料条件恰好相同。

验证补充：`node test/exactPlannerComparison.test.js` 使用真实 HiGHS 比较三种投入结果，并验证采用、云端恢复、取消和单项错误隔离。

规划模式、培养与体力条件、方案对比共用一个「日程规划」面板，以内部区域和分隔线连接设置与结果。模式切换常驻，条件可折叠；对比起点提示统一放在方案对比内部。

## 一次性储备

目标天数模式的第一列同时配置期限和多条储备。每条输入名称和数量，默认从规划起始日可用，由求解器选择一次性整笔领取的日期；只有已提取体力需要勾选「必须在起始日使用」。不要求用户预先输入领取日期，可独立领取的份数分别添加。

每条储备使用每日二元变量表示领取或不领取，整期最多一次；固定起始日的储备约束在当天领取。日末结余不跨日结转，也不把同一笔储备拆给不同日期。三个对比项使用相同储备规则。最低白金币证明成立后，在相同费用与已有完成日期下尽量减少不必要的领取；此附加优化超时不影响费用证明。因免费体力或其他储备已经足够而未领取的储备会明确列出。

结果展示每条储备的领取日期、未领取项及总量；每日预览同时展示体力结余。目标天数的最低费用结果优先展示，固定购买档位作为对照。旧 `initialExtra` 仍表示仅第一天额外体力，供兼容旧算法调用；新界面使用 `reserveSources`。

## 整行储备管理与当前设置最短天数

目标天数模式的条件区上排为期限、推荐偏好、可刷层数；其下整行管理体力储备。起始日额外体力为已到账体力，仅计入第一天；待领取储备为多笔可择日整笔领取的体力，默认从起始日可用。每笔仅填写名称和数量，不再使用固定日期复选框。桌面布局左侧为起始日体力，右侧为紧凑储备列表；窄屏上下排列。

结果区新增独立的「计算当前设置最短天数」按钮。它保留当前购买档位、派遣、层数、起始日体力与待领取储备，以整体最早完成为目标，从规划起始日起最多求解 90 天，不受目标天数输入限制。该结果不替换期限内最低白金币与固定购买对比结果；所有结果在输入变化后统一失效，不自动改写日程。

## 期限不足的补足候选

当前界面以「计算期限与补足方案」替换独立最短天数按钮。当期限对比中有方案已证明不可行时，用户可主动计算原期限与逐日延长 1–7 天的候选（最多 90 天、去重）。每档分别求解：保持当前购买次数所需的最少额外体力；不增加外部体力、仅调整每日购买次数的最低累计白金币。后者沿用实际累计阶梯价格与每日最多 8 次限制，不用统一单价换算体力。差额以相同完成天数下当前购买档位的预算为参照，并明确原预算未必可完成。

额外体力使用每日 0–1500 的整数变量，先优化整期总量，因此可用储备会优先用于降低外部补充需求；仍保留每日历练次数、开放层数及一次性储备约束。1500 是用户提供的估算，统一配置于 `PLANNER_RULES.maxDailyExtraStamina`，当前口径仅限制新增外部补充，原有获取与已拥有的储备另计。独立结算及采用前校验也检查每日补充总量，不能拆成多条规避。结果是需要额外获取体力的需求，不代表存在可购买渠道，不自动写入日程；每日详情显示补充量与购买次数。即使补充体力仍不可行时提示检查次数上限和获取途径；未知或超时不作不可行证明。

补足候选以最少额外体力或最低白金币为求解目标，在每项时限内保留已校验的可行解。界面保守标记「已验证可行，不保证最优」。最少补充总量求得后，在剩余时间内固定总量上限，再降低每日补充峰值，避免将补充集中在某一天；附加求解超时仍保留此前合法方案。设置了派遣时，每档期限增加「减少派遣并补体力」候选；只允许减少自动日的洛阳、寿春派遣，不增加次数或改动未来手工日。 在最少额外补充总量下，进一步最小化取消的派遣次数，使可用储备先抵消缺口，储备足够时保留全部派遣。该优先级使用由派遣次数上限推导的严格权重：一单位额外体力的权重大于整期最多可取消的派遣次数；不会为保留派遣增加额外补充。后续均衡每日补充时同时锁定派遣减少次数上限，避免再次牺牲派遣。结果列出各日减少次数、释放体力和仍需补充的体力，供用户决定，不自动修改设置。常规全局最优和期限内最低白金币主方案仍保留最优求解。

补足计算交互改为逐日方块进度，从原期限逐日延长到 7 天后（最多 90 天）。期限以暖纸色小日历呈现，由真实任务事件驱动计算、找到方案、暂不可行和未确定状态。日历和方案轻量入场，可行状态短暂表情反馈；所有运动均支持减少动态效果。方案简报展示额外体力、白金币及已领取储备，支持键盘选择与窄屏横向浏览。不输出补足不可行结果卡，派遣变化并入每日安排。点击简报查看日程，确认额外体力、购买与派遣后可采用；采用重新校验方案，替换当前及未来安排并固定各日计划，保留底层历史但隐藏旧阶段。期限不足时，右侧补足按钮为主操作，重新计算为次操作。
