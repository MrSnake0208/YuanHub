# 密探面板无感采样与公式完善路线

状态：延后实施  
最后整理：2026-08-23  
涉及仓库：YuanHub 前端、BackEndV3-Share 后端  

## 1. 决策摘要

平台尚未正式上线，当前没有足够真实流量验证玩家数据分布、漏填率、样本重复率、异常阈值和管理员审核工作量。因此暂不整体实施完整采样系统。

采用“资料治理 → 最小原始留样 → 真实数据分析与审核”的分阶段路线：

1. 当前保留并治理已有公式资料；
2. 上线前如确有必要，只实现默认关闭的最小原始留样层；
3. 上线后出现真实样本，再实现 m 反推、稳健统计和完整后台页面。

完整后端规格已经冻结在：

- [后端实施 Prompt](./backend-implementation-prompt-operator-combat-observations.md)

当前数据基线位于：

- [面板数据覆盖统计](./operator-combat-data-coverage-2026-08-23.md)

## 2. 已确认事实

### 2.1 公式边界

- 命盘和天赋不影响基础攻生面板，不采集、不入签名；
- 化极小节点属于固定值项，在百分比乘区之前；
- 星石只考虑橙色品质，不存在同名不同属性版本；
- 奇闻只有 attack/hp 纯数值参与基础面板；
- 普通密探与 SP 使用不同公式族，SP 当前规则未知；
- 自动计算值不能回流成为实际观测样本。

### 2.2 当前来源字段

- `scan`：后端自动采集/识图上报的 `combat_stats.observed_attack`、`observed_hp`；
- `manual`：用户通过卡片或完整编辑器保存的 `manual_attack`、`manual_hp`；
- `admin`：未来由管理员明确录入的基准候选；
- `imported`：备份恢复或普通导入，默认不作为公式样本。

后端目前会把 scan 的 observed 值镜像到 manual 字段供前端展示；未来留样时必须读取原始 observed 字段，不能重复生成 manual 样本。

### 2.3 当前覆盖快照

前端图鉴目录共有 121 位密探，本地面板表有 89 条普通密探记录。严格五档口径下：

| 状态 | 数量 |
|---|---:|
| 普通密探五档完整 | 44 |
| 部分档位缺失或数据结构异常 | 45 |
| 普通密探本地完全无规则 | 30 |
| SP 规则未知 | 2 |
| 仍需补充信息 | 77 |

这 77 位不等于全部需要向玩家重新采集。必须先区分公开资料尚未同步、现有资料损坏和确实缺样本三种情况。

已发现的明确问题：

- 陆逊 `Level_HP` 有 5 项、`Level_ATK` 只有 4 项，现有裸数组存在档位错位风险；
- 本地规则尚无司马孚、赵云，而 BWiki 当前页面已更新到二者，并注明司马孚缺 90+15；
- 22 位 3 星密探本地无普通规则，BWiki 魂魂表仅可作为待核验候选来源；
- 2 位 SP 应单独留样研究，不能套普通化极公式。

## 3. 当前暂不实施的范围

以下工作整体延后：

- `operator_combat_observation` 正式样本库；
- 每条样本自动反推 x/y/m；
- median/MAD 异常检测；
- 管理员接受、排除、恢复样本；
- SP 公式推断；
- `/operator/admin/combat-data` 完整管理页面；
- 自动把候选 m 提升为生产公式；
- 面向用户的采集进度或贡献反馈。

延后不代表取消。后端完整模型、接口和测试要求保留在实施 Prompt 中。

## 4. 阶段 0：资料治理

该阶段可在正式采样前独立完成，且会直接改善现有自动计算。

### 后端/共享资料

1. 对照最新 BWiki 数据重新生成规则资料；
2. 输出 121 位图鉴与公式表的动态覆盖审计；
3. 将标准档位从裸数组改成明确键：
   - `50_7`
   - `60_9`
   - `80_13`
   - `90_15`
   - `100_17`
4. 化极节点也使用明确节点键或严格长度校验；
5. 修复并测试陆逊错位资料；
6. 为每项规则记录来源、来源版本、核验状态和公式版本；
7. 明确区分：
   - `complete`
   - `source_sync_needed`
   - `sample_needed`
   - `data_malformed`
   - `missing_rules`
   - `sp_research`
   - `verification_only`

### 前端

1. 继续使用当前自动计算器，但不得把不完整数组静默当作完整档位；
2. 对缺规则或结构异常的密探显示明确降级说明，不猜测数值；
3. 修正规则导入后补充计算单元测试，覆盖：
   - 五个标准档位；
   - 化极中间节点；
   - 橙色固定值星石；
   - 橙色百分比星石；
   - 星石组合；
   - 奇闻 attack/hp；
4. 从 `combatInputSignature` 移除不参与计算的奇闻 special；
5. 保持命盘不进入面板签名。

## 5. 阶段 1：上线前可选的最小留样层

只有在希望保留上线初期珍贵样本时实施。该阶段不做统计后台。

### 启动条件

- current PATCH 与 scan 上报协议已稳定；
- 数据用途说明已经上线；
- 能通过测试账号产生 scan/manual 两种真实样本；
- 后端有不会阻断用户保存的 after-commit/event 处理方式；
- 管理员能通过 API 或最小工具控制采集开关。

### 后端最小范围

- 建立逐密探 collection policy，默认关闭；
- 建立原始 observation 存储；
- scan 使用原始 `observed_*`；
- manual 使用本次请求显式提交的 `manual_*`；
- 保存服务端权威等级、修为、化极、六槽星石、奇闻 attack/hp 快照；
- 服务端生成 canonical signature；
- 实现幂等、重复保存合并、去标识化贡献者键；
- imported 不采样；
- 采集失败不影响 current/scan 正常保存；
- 子账号删除时删除对应 observation；
- 暂不计算 m、不判异常、不提供完整审核页面。

### 前端最小范围

- 用户正常使用卡片和完整编辑器即可，不增加提交按钮或确认弹窗；
- 保留清晰的数据用途说明和详情链接；
- 不额外提交自动计算值；
- scan/manual 继续沿用现有字段，不新增 `passive_save`；
- 如后端暂时没有管理员 UI，仅增加受管理员权限保护的最小采集开关界面，不提前建设样本分析表。

## 6. 阶段 2：真实数据分析与管理员后台

### 启动条件

满足以下条件后再进入：

- 至少出现多个开启采集的目标密探；
- 至少部分相同 `operator + level + elite` 分组拥有 3 个独立贡献者；
- 已观察到真实重复、漏填和异常案例；
- 管理员能够明确提出实际审核筛选需求；
- SP 或新密探已有足够输入完整的原始样本。

### 后端工作

- Kotlin 权威公式 evaluator；
- 每条样本计算 x/y/m 与 breakdown；
- 公式版本变化后可重算；
- 按 `game + formulaFamily + operatorId + level + elite + dimension` 分组；
- 中位数、MAD、absolute tolerance 和 provisional consensus；
- 自动标异常但不自动排除；
- pending/accepted/excluded 审核状态和审计；
- coverage/detail/policy/sample 管理员 API；
- 管理员手动录入基准候选；
- 仍不自动发布生产公式。

### 前端管理页面

新增页面：

```text
/operator/admin/combat-data
```

遵循仓库页面规范：在 `src/pages/operator/` 建页面，并在 `src/router/routes.js` 注册路由。页面仅管理员可访问。

#### 6.1 覆盖总览

需要展示：

- 密探、稀有度、属性、职业、普通/SP；
- 采集开关；
- workflow status；
- 50+7、60+9、80+13、90+15、100+17 分档覆盖；
- attack/hp 有效样本数与独立贡献者数；
- accepted/excluded/suspicious 数；
- 最近样本时间和公式版本；
- 外部资料待同步说明。

筛选至少包括：

- 仅看开启采集；
- 仅看确实缺样本；
- source sync needed；
- data malformed；
- SP research；
- suspicious/conflict；
- 属性、职业、稀有度和名称搜索。

“本地缺规则”和“需要玩家采样”必须使用不同视觉状态，不能共用一个红色缺失标签。

#### 6.2 密探样本详情

每条样本展示：

- 来源标签：识图自动采集 / 玩家手动校正 / 管理员录入；
- 匿名贡献者短标识；
- 等级、修为、化极；
- 六槽星石；
- 奇闻 attack/hp；
- 实际攻击/生命；
- x/y/m 与公式 breakdown；
- 组中位数、绝对/相对偏差、robust z-score；
- quality flag 与 review status；
- 采样时间、公式版本和审核历史。

支持：

- 接受样本；
- 软排除并要求填写原因；
- 恢复排除；
- 按来源、档位、状态筛选；
- 展开完整计算过程；
- revision 冲突时重新获取数据，不静默覆盖其他管理员操作。

#### 6.3 交互与视觉

- 沿用纸底、暖白卡、暖棕正文和金橙强调；
- scan/manual/admin 使用克制的描边标签，不使用大面积品牌蓝；
- 异常只作为警示，不等于已排除；
- 表格在桌面端优先，窄屏切换为可展开记录卡；
- 所有开关、审核操作有明确 focus、disabled、loading、success/error 状态；
- 排除属于重要但可恢复操作，需要原因确认，不使用浏览器原生 confirm；
- 不使用原生 title 承载关键解释，采用站内 tooltip/popover；
- 样本中的用户身份只能显示匿名短标识。

### 前端 API 层

后端交付最终接口后，在 `src/api/operator.js` 增加对应封装，预计包括：

- 获取覆盖总览；
- 获取单个密探详情和分页样本；
- 更新采集 policy；
- 接受/排除/恢复样本；
- 管理员录入样本；
- 读取公式资料缺口和触发重算（如果后端提供）。

不得在后端尚未交付实际 OpenAPI 契约前写死临时字段。

## 7. 阶段 3：公式候选发布

只有管理员审核形成稳定共识后考虑，且与样本系统分开交付。

建议流程：

```text
原始样本
→ 候选 m 与共识
→ 管理员核验
→ 生成公式资料变更草案
→ 独立审核/测试
→ 发布新 formula version
```

禁止样本数量达到阈值后自动改线上公式。生产规则变化必须可审计、可回滚，并运行前后端 golden tests。

## 8. 前端测试计划

阶段 1 最小留样：

- 手动值保存请求仍使用 `manual_* + source=manual`；
- 自动显示值不会伪装成 manual 样本；
- scan 返回值不会被前端再次作为 manual 提交；
- 数据说明链接在桌面和移动端可见、可聚焦；
- 后端采集失败不改变用户保存成功状态。

阶段 2 管理后台：

- 路由权限与非管理员降级；
- 覆盖筛选、分页和空状态；
- policy 开关 revision 冲突；
- scan/manual/admin 来源展示；
- suspicious 与 excluded 不混淆；
- 排除原因必填、恢复和错误回滚；
- 长星石名、四位数奇闻、长公式 breakdown 不横向撑破页面；
- 375px、768px、桌面宽度响应式；
- 键盘导航、焦点可见、popover 不被卡片覆盖；
- API 契约测试锁定 snake_case 字段和错误码。

## 9. 启动时的第一批任务

当决定恢复该项目时，按以下顺序开工：

1. 重新生成一次实时覆盖统计，不直接沿用 2026-08-23 的 77；
2. 同步 BWiki 和其他可信公开资料；
3. 将剩余缺口由 `source_sync_needed` 人工确认成 `sample_needed`；
4. 决定只做阶段 1，还是已有足够数据直接进入阶段 2；
5. 后端按本目录 Prompt 实施并交付实际接口文档；
6. 前端依据实际接口实现管理页面；
7. 先用测试账号和少量密探灰度开启；
8. 样本足够后才启用异常分析和公式候选流程。

## 10. 非目标与风险

非目标：

- 不采集命盘、备注、favorite、养成状态和成长目标；
- 不为采样增加用户操作；
- 不用 SP 样本猜普通公式；
- 不让自动计算值自证公式正确；
- 不自动发布公式。

主要风险：

- 玩家手动值与其他养成输入不同步；
- 扫描 OCR 有误；
- 公开资料版本与游戏版本不同；
- 裸数组缺项造成档位错位；
- 同一贡献者重复保存造成伪样本量；
- 样本量不足时统计结果不稳定；
- 管理员页面过早实现导致交互重做。

这些风险正是完整功能延后、先做资料治理和最小留样的原因。
