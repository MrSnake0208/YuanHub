# 密探图鉴与养成追踪产品设计

状态：设计定稿草案（前端可执行部分已拆分）  
适用页面：`/operator`、`/operator/quick`，以及库存页的密探心纸流水联动  
更新时间：2026-08-20

## 1. 产品定位

密探模块不是单一的角色列表，而是一个面向单个游戏子账号的养成工作台：

1. 图鉴用于认识和查找全量密探。
2. 当前养成用于维护账号已经拥有的密探状态。
3. 养成追踪用于根据特别关注名单和库存流水决定下一步资源投入。

“特别关注”是用户维护的养成目标集合，不只是列表排序或过滤条件。关注名单按子账号隔离，与密探心纸库存和库存流水关联，但不进入库存流水本身。

## 2. 页面信息架构

### 2.1 一级视图

`/operator` 保留三个一级 Tab：

| Tab | 用户问题 | 数据范围 | 默认排序/结构 |
|---|---|---|---|
| 图鉴 | “有哪些密探？我还缺谁？最近出了谁？” | 公共目录全量，登录后叠加拥有状态 | 最新实装优先；紧凑头像网格 |
| 当前养成 | “我现在把谁练到了什么程度？” | 当前子账号有养成记录的密探 | 等级 → 星级节点 → 修为；数据列表 |
| 养成追踪 | “我下一步该练谁？材料够不够？收集速度如何？” | 特别关注密探、养成状态、心纸库存、库存流水 | 目标优先；仪表盘 + 目标列表 |

图鉴中的“全部 / 已拥有 / 未拥有”仍然保留，因为它回答的是目录覆盖问题；它不能替代当前养成，因为当前养成提供的是可比较、可操作的养成台账。

### 2.2 图鉴

图鉴顶部工具栏：

```text
搜索 · 版本 · 属性 · 从属 · 全部/已拥有/未拥有 · 排序：最新实装
```

筛选与排序规则：

- 默认按密探 ID 中的发布序号降序，无法解析序号的 ID 排在最后。
- 可选排序：最新实装、等级、星级节点、修为、稀有度、名称。
- 特别关注不单独复制一套列表，而作为状态和可选过滤条件接入图鉴。
- 登录且选择子账号后，卡片允许加入/取消特别关注。
- 未登录时仍可浏览全量目录，但关注和养成编辑需要登录及子账号。

图鉴卡片只保留目录浏览需要的信息：头像、名称、官方属性图标、拥有状态和少量操作。静态稀有度不再以“5★ · 阳”文字标签堆在头像下方。

### 2.3 当前养成

当前养成默认只显示该子账号已有养成记录的密探，按以下顺序排序：

1. 等级降序；
2. 星级节点降序；
3. 修为降序；
4. 发布序号降序作为稳定兜底。

推荐采用横向数据行而不是与图鉴相同的头像网格：

```text
头像  名称 + 属性图标/从属    Lv 90    5星·3    修为 17    命盘 1/2    星石方案    编辑
```

当前养成的功能重点：

- 快速比较等级、星级节点和修为；
- 直接查看命盘方案数量和当前星石方案；
- 快速打开编辑；
- 以后承载批量筛选、批量编辑和目标设置。

如果账号没有养成记录，空态应引导“快捷导入”或“从图鉴选择密探”，不能只显示“暂无数据”。

### 2.4 养成追踪

养成追踪的标题建议为“养成追踪”，副标题为“特别关注的密探与材料进度”。“特别关注”作为名单名称保留在说明和操作中。

顶部概览建议显示：

- 关注密探数量；
- 已拥有 / 未拥有关注密探；
- 当前持有心纸总数；
- 当前周期获得心纸；
- 最近 7 天或 30 天心纸日均；
- 本期获得过心纸的关注密探数；
- 最近最久未获得心纸的关注密探。

下面展示目标列表。每个目标至少包含：

```text
头像 + 属性图标  密探名称
心纸：当前 / 目标
等级：当前 / 目标
修为：当前 / 目标
命盘：当前方案数 / 2
材料：已知缺口摘要
流水：周期获得量 · 日均 · 最近获得日期
操作：设置目标 / 编辑养成 / 查看流水
```

目标列表不应把“加入关注”与“设置养成目标”混为同一个动作：星标只是加入追踪，目标等级、目标修为和目标星级是另外的用户设置。

目标列表上方增加“关注目标总账”：先合并所有关注密探的等级、修为和化极需求，再对共享材料库存抵扣一次。单个密探行仍可展示“如果只养这一位”的独立缺口，但必须标明是单人测算，不能把同一份库存分别抵扣后再汇总为整体缺口。心纸按密探 ID 分别抵扣，不作为可在密探之间调配的共享材料。

## 3. 数据能力与计算边界

### 3.1 当前前端已经能做的真实统计

库存接口和已有统计逻辑已经提供：

- 当前密探心纸数量：`GET /v1/inventory/current?entity_type=agent`；
- 指定时段获得量：`GET /v1/inventory/acquired?entity_type=agent`；
- 奖励流水分页与明细：`GET /v1/inventory/records`；
- 关注名单：`GET/PUT/DELETE /v1/inventory/agent-favorites`；
- 关注心纸周期总量、排行、覆盖率、最久未获得、幸运日等派生统计。

这些数据可以立即支持“收集进度”和“收集速度”面板，但必须区分：

- 当前持有量：库存投影的余额；
- 周期获得量：指定时间范围内的流水增量；
- 速度：周期获得量 / 日历天数，或周期获得量 / 有流水的活跃天数；
- 目标缺口：目标数量 - 当前持有量，不能用周期获得量代替。

### 3.2 本地 Wiki 页面已经提供的静态需求数据

`docs/reference/yuan-operator-calculator/` 保存的是页面完整 HTML 和依赖资源，计算逻辑与数据都内嵌在 HTML 中，不是截图。当前页面元数据为 Wiki 修订号 `93628`，页面最后编辑时间为 2026-07-05，抓取缓存时间为 2026-08-19。等级、修为和化极消耗视为固定规则，YuanHub 不提供版本切换或版本维护界面。

从修订号 `93628` 的脚本可以直接提取出以下数据：

| 养成维度 | 已有数据 | 计算方式/注意事项 |
|---|---|---|
| 等级 | 1-100 每级经验；10、20、30…90 级突破门槛；通用材料、五铢钱、70/80 级职业专属材料 | 按 `now + 1 .. target` 累加经验；只有跨过门槛才计突破材料；职业专属材料按破军、龙盾、岐黄、神纪、诡道分别统计 |
| 化极/星级节点 | `1-0` 到 `4-5`、一至四星升星、觉醒共 25 个节点；每节点心纸和五铢钱，觉醒另有装金玻璃 | 按节点序号累加 `now + 1 .. target`；心纸应与账号中对应密探的 `entity_type=agent` 库存关联 |
| 修为 | 修为 1-17 的逐级材料消耗与五铢钱；风火、地水、阴阳三套材料序列 | 先累加目标区间，再抵扣“已有材料”；页面还根据历练 1-12 的奖励数组给出体力和关卡策略 |
| 好感 | 绝密/机密/隐密的若干解锁阈值与金锁消耗表 | 可作为后续扩展；当前不是完整的好感目标计算器 |

因此，Wiki 数据足以让 YuanHub 做出“目标值 → 总需求 → 当前库存抵扣 → 净缺口”的第一版计算器。当前 `src/data/inventory/catalog.js` 已覆盖页面列出的修为材料、突破材料、三类兵书和装金玻璃；心纸不是通用物品，而是对应密探的 `agent_id` 数量。五铢钱只展示目标总需求，不进入库存缺口、收集速度或 ETA 规划。

等级经验的三类兵书是三种经验面额，不是三份需要同时扣除的材料。应先统一折算经验：

```text
owned_exp = 残卷数量 × 100 + 全卷数量 × 1000 + 六韬数量 × 10000
exp_gap = max(required_exp - owned_exp, 0)
```

Wiki 页面当前只是分别显示 `ceil(required_exp / 面额)`，不能把三个显示值相加为总需求。另外，觉醒节点数据中存在 `装金玻璃 × 1` 字段，但原页面只渲染心纸和五铢钱；修为逐级数据中也有五铢钱数组，但合并后的 v9 结果区没有汇总展示。YuanHub 提取数据时应保留这些字段，并为它们单独补测试。

### 3.3 不能直接把 Wiki 脚本当成后端契约的部分

下面这些内容仍需要 YuanHub 自己定义和校验：

- **数据主键**：Wiki 使用中文材料名和图片 URL，库存使用稳定 `item_id`/`agent_id`。不能在运行时依赖中文名称或外链图片匹配。
- **职业/属性口径**：等级突破使用五种从属，修为使用风火、地水、阴阳三类，需在适配层明确映射，不能把两套枚举混为一谈。
- **算法可解释性**：修为区块的历练策略是页面内置的贪心算法；YuanHub 应至少展示“材料净需求”和“估算体力”，并标注策略为估算，不应把它当成唯一最优解。
- **星石**：本页面没有星石等级/经验星石消耗表。星石方案可以先保存和展示，但星石升级缺口必须等待另一份可靠数据源。
- **账号状态**：Wiki 只给静态总需求，不知道用户当前等级、节点、修为、库存或流水，这些必须来自子账号养成记录和库存接口。

提取后的规则应落成前端静态资源，而不是在 Vue 组件运行时解析 HTML：

```text
target_stage + profession_or_attribute?
  -> item_id + required_count
```

心纸需求在计算时动态绑定当前密探 `agent_id`；`target_stage` 至少覆盖 `level`、`xiuwei`、`star_node`、`awakening`。

### 3.4 缺口、速度与 ETA 的计算边界

接入上述需求资源后，缺口可以这样计算：

```text
net_gap(item) = max(required(item) - current_stock(item), 0)
```

速度仍只能由 YuanHub 流水计算，Wiki 不提供速度：

```text
daily_rate(item) = acquired_in_window(item) / calendar_days
                 或 acquired_in_window(item) / active_days
eta_days(item) = net_gap(item) / daily_rate(item)
```

UI 必须同时显示统计窗口和口径。没有流水、窗口过短或速度为 0 时，显示“样本不足/暂无 ETA”，不能伪造日期。多个材料的目标完成日应按最慢的正缺口材料计算，并允许用户展开查看每项材料的速度来源。五铢钱始终排除在该计算之外。

## 4. 版本与子账号

一个子账号原则上对应一个游戏版本。版本是账号级上下文，不应每次保存都依赖页面顶部筛选猜测。

推荐账号字段：

```json
{
  "id": "acc_xxx",
  "name": "大号",
  "game_scope": "如鸢 | 代号鸢 | universal"
}
```

交互规则：

- 创建子账号时允许选择版本；
- 旧账号没有版本时，首次编辑或首次快捷导入必须选择版本；
- 选择后后续表单默认跟随账号版本；
- `universal` 表示不区分版本，只保存一份通用状态；
- 查询筛选中的“全部版本”和保存目标中的“不区分版本”使用不同文案；
- 不再使用“通用（全部）”或“全部（通用）”这种混合说法。

当前页面把顶部筛选为“全部”时写入 `game: null`。在后端明确该字段语义前，前端不能把它解释成“同时写入两个版本”。

## 5. 命盘与星石方案

命盘方案与星石方案是两套完全独立的收藏/选择数据：

```text
命盘方案：最多 2 套，可命名
星石方案：数量不限，可命名
命盘方案和星石方案不自动绑定
```

推荐概念模型：

```text
disc_loadouts:
  id, name, discs, is_active

stone_loadouts:
  id, name, star_stones, is_active
```

旧数据中的 `discs` 和 `star_stones` 分别迁移为默认命盘方案和默认星石方案。用户切换命盘方案时不应自动切换星石方案，反之亦然。

前端编辑界面最终应分成：

1. 基础养成；
2. 命盘方案；
3. 星石方案；
4. 养成目标。

命盘最多两套和星石无限套属于后端约束，不能仅在前端模拟。方案列表也不应全部重复写入每一条养成快照；推荐由后端以独立资源保存，快照只记录当前状态和当前方案 ID。

## 6. 卡片与视觉规范

### 6.1 图鉴卡片

推荐结构：

```text
[关注 Star]             [头像 + Lv/未拥有]
                         名称
                         属性图标 · 从属
                         [编辑 Pencil]
```

- `Star` 固定在头像右上角，使用 Lucide 图标和 `aria-pressed`；
- `Pencil` 固定在卡片右下角，使用 Lucide 图标，点击区域至少 44×44px；
- 卡片高度稳定，不因按钮或动态文案改变网格布局；
- 静态稀有度用头像框层级、边框细节或详情文本表达，不用长文字标签占据卡片主空间；
- 属性使用官方图标作为主识别，颜色仅作辅助，不可只靠颜色区分；
- 官方属性图标来源：`/home/syoius/MaaYuan-Share-frontend/public/assets/prof-icons`；
- 需要复制到本仓库 `public/assets/prof-icons/`，映射 `yin/yang/fire/wind/water/earth/chaos.png`。

### 6.2 当前养成与养成追踪

当前养成使用高密度数据行，养成追踪使用目标卡/目标行。两者都应保留头像和属性图标，但信息重点不同：

- 当前养成突出“当前状态”；
- 养成追踪突出“当前值、目标值、缺口和速度”。

编辑界面采用宽编辑面板：头部固定显示密探身份、当前子账号和版本上下文，中间内容区独立滚动，底部操作栏固定显示状态、取消和保存。这样命盘、星石和后续养成目标可以继续纵向扩展而不遮挡保存操作；移动端使用接近全屏的编辑面板。

页面继续使用设计规范中的纸底、暖白、奶油、暖棕、茶棕和蜜黄；官方属性图标是内容资产，不扩展页面主色板。不得使用纯黑、大面积海盐蓝或黑底黄字。

### 7.3 必须等待后端/数据契约

- [ ] 命盘最多 2 套的持久化接口和导入导出结构。
- [ ] 星石无限套的持久化接口、分页/懒加载策略和当前方案选择。
- [ ] 命盘方案与星石方案独立切换，不互相覆盖。
- [ ] 旧 `discs` / `star_stones` 数据迁移为默认方案。
- [ ] 养成目标字段：目标心纸、目标等级、目标修为、目标星级节点及其账号/密探归属。
- [ ] 将浏览器本地保存的养成目标迁移为后端账号级字段，并补充跨设备同步。
- [ ] 明确方案是否作为独立资源保存，避免将无限星石方案重复写入每条 `operator_snapshot`。

## 8. 验收标准

完成当前前端阶段后，用户应能：

1. 在图鉴中按最新实装顺序浏览全部密探，并看到官方属性图标。
2. 在图鉴中加入/取消特别关注，切换账号后关注状态不串号。
3. 在当前养成中快速比较等级、星级节点和修为，而不是重复浏览图鉴卡片。
4. 在养成追踪中看到关注密探的当前心纸、周期获得量、速度和最近流水状态。
5. 对已配置的等级、化极和修为需求看到材料缺口；没有对应版本、映射或流水数据时明确知道原因，不会看到伪造数量或 ETA。
6. 在首次编辑或快捷导入时明确知道保存对应的游戏版本。
7. 使用键盘和移动端完成关注、筛选、编辑入口和 Tab 切换。
